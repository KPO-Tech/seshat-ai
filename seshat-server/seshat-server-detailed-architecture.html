Frontiere principale

Le serveur n'est pas seulement un proxy IAM. Il execute directement deux chemins Seshat: chat workspace interactif et runs automation cloud.

Securite runtime

Les deux integrations SDK qui peuvent atteindre des outils imposent RequireSandbox=true. Les credentials sont decryptes seulement au moment de resolution.

Mode multi-tenant

Les domaines org-scoped dominent: IAM, settings, RAG, automation, registries. Preferences/memories/quotas restent user-scoped.

Persistance

SQLite est le defaut local; Postgres est supporte. Le stockage de fichiers et vectors est interchangeable via config, avec HNSW local par defaut.

Sources principales lues: cmd/server/main.go, internal/server/app/app.go, internal/server/api/routes.go, internal/server/db/models.go, internal/server/automation/*, internal/server/workspacechat/*, internal/server/knowledge/*, et services secondaires sous internal/server/*. Connecteurs Cloud

Type
Existe ici
Ce que fait le code
Ce que ca n'est pas
LLM provider settings/api/v1/provider-settings
Oui, central.
Stocke et resout les credentials LLM par organisation, avec fallback platform. C'est ce qui debloque les jobs execution_target=cloud et le chat workspace.
Ce n'est pas un connecteur OAuth utilisateur vers une application tierce; c'est une configuration de fournisseur de modele.
Web search providers/api/v1/web-search-provider-settings
Oui.
Centralise Tavily, Exa, Jina, LangSearch et SearXNG, plus une policy allow/block domains par organisation.
Ce n'est pas un connecteur general de donnees cloud; seulement la recherche web appelee par le runtime.
MCP server configs/api/v1/mcp-server-configs
Oui, mais config-only.
Stocke command/url/env/headers chiffres pour que les backends connectes recuperent une configuration partagee.
L'execution MCP ne se fait pas dans seshat-server; les commentaires disent qu'elle reste locale cote membre/backend connecte.
Identity providers/api/v1/providers
Oui.
Gere les fournisseurs OIDC/OAuth2/SAML pour login, auto-link et auto-provisioning membership.
Ce n'est pas un connecteur metier vers les fichiers/messages/calendriers de ces providers.
Client applications/api/v1/applications
Oui.
Enregistre les clients OAuth/OIDC autorises a parler au control plane.
Ce n'est pas une marketplace d'integrations cloud; c'est l'auth client-side/control-plane.
Storage cloudS3 via config serveur
Oui, pour artifacts.
Permet de stocker les fichiers knowledge-base via provider local ou S3, configure par SESHAT_SERVER_STORAGE_PROVIDER et variables S3.
Pas de GCS/Azure detecte dans ce code serveur; pas de connecteur utilisateur OAuth a un drive cloud.
Device connectors/api/v1/device/*
Oui, sous forme de protocole.
Le cloud cible un seshat-backend local enregistre; le device poll/claim/start/heartbeat/complete/fail les runs.
Ce n'est pas un connecteur SaaS; c'est un pont vers une execution locale.
Connecteurs SaaS generiquesDrive, Gmail, SharePoint, S3, MCP actions
Pas comme domaine serveur dedie.
Le serveur peut stocker des configs MCP ou des presets d'agents qui referencent des outils, mais les comptes OAuth utilisateur et les implementations de connecteurs ne vivent pas ici.
Ils sont dans seshat-backend: internal/knowledge/gdrive, internal/inbox/gmail, internal/knowledge/sharepoint, internal/knowledge/s3, internal/mcp/action.
