# Audit SeshatOS — 2026-08-10

Perimetre: `seshat-backend`, `seshat-ui`, frontieres avec `seshat` (runtime) et
`seshat-server` (cloud/entreprise). Objectif: rendre l'application desktop
locale fiable, complete et testable en mono-utilisateur avant de renforcer la
couche entreprise. Cet audit ne recouvre pas le terrain deja couvert par
`docs/helps/audit-2026-08-02.md` (tooling, `make setup`, `make deploy-up`, CI,
versions Node/Go) — se referer a ce document pour ces sujets, toujours valides.

Methode: revue de code en lecture seule sur les cinq axes suivants, chacun
verifie fichier par fichier avec citations precises: domaines backend locaux
et agents produit, frontend `seshat-ui`, frontiere local/cloud (`cloud*` vs
`seshat-server`), securite/permissions, modele de donnees et empaquetage
desktop.

La Phase 1 de la section 8 a ete executee le jour meme. Deux constats du

  c'etait le mauvais sens de correction. Decision prise avec l'utilisateur:
  garder la constante figee, corriger toute la documentation et le
  code mort autour (voir "Corrections effectuees" ci-dessous). Les sections
  1, 3 et 7.1 ci-dessous restent affichees dans leur version originale pour
  tracer le raisonnement, mais sont **perimees** sur ce point precis — se fier
  a cet addendum.
- **`requireRole("admin")` sur `/skills/repos` n'est pas une incoherence a

  point 7) recommandait de migrer cette route vers `requireScopedPermission`
  pour la rendre coherente avec le bypass mode-local du reste de l'API.

## 1. Resume executif

Le runtime est globalement sain: le decouplage `seshat-backend` (local) /
`seshat-server` (cloud) est reellement bien concu au niveau code — 13 paquets
`cloud*` cote backend, tous cables, tous avec un repli local propre, et
`seshat-ui` ne parle jamais directement a `seshat-server` (verifie
exhaustivement, zero occurrence). La securite de base est correcte: chiffrement
AES-256-GCM des secrets, hachage des mots de passe/API keys, IPC Electron
majoritairement borne a des racines autorisees, controle d'acces par
proprietaire sur les fichiers. Les migrations SQL sont propres et versionnees.

Mais quatre problemes structurels empechent aujourd'hui l'app desktop d'etre
"complete et fiable en mono-utilisateur" au sens ou le demande cet audit:

1. **Le mecanisme de bascule local/connecte n'existe pas tel que documente.**
   `SESHAT_SERVER_URL`, decrit partout (ROADMAP.md, commentaires de code) comme
   le variable d'environnement qui active le mode connecte, **n'existe dans
   aucun fichier Go** (grep exhaustif: zero occurrence en dehors des
   commentaires). Le vrai mecanisme est une constante Go figee
   (`defaultServerURL = "http://localhost:8081"`) plus une sonde de
   disponibilite au demarrage. Cote `seshat-ui`, une variable
   `SESHAT_DEFAULT_SERVER_URL` est plombee jusqu'au sous-processus mais le
   binaire Go ne la lit jamais. Resultat: personne ne peut aujourd'hui
   configurer honnetement le mode connecte en suivant la documentation.
2. **Le desktop local embarque un IAM multi-tenant complet** (organisations,
   workspaces, groupes, roles) cree automatiquement pour chaque installation
   mono-utilisateur, avec des routes CRUD completes non protegees par un
   garde-fou "mode local". C'est la source principale de pollution
   conceptuelle: schema de donnees, API, et jusqu'a l'UI (Admin Console
   visible et vide) heritent tous de ce choix.
3. **Une fonctionnalite CRM complete (`prospecting`) est du code mort** — 
   service, scoring, geocoding, 4 tables SQL, entierement ecrits, zero route,
   zero outil agent, zero reference dans `app.go`. A trancher: terminer le
   branchement ou supprimer.
4. **`seshat-ui` n'a aucun systeme de composants partage.** Chaque page
   reimplemente son propre etat de chargement/erreur/vide/toast et son propre
   bloc CSS — d'ou les incoherences visuelles listees en section 4/UX et un
   cout de maintenance croissant.

A cote de ca, plusieurs fonctionnalites sont deliberement "Coming soon"
(Team, Projects → Notebook/Data Lab, Knowledge → catalogue public) et
honnetement etiquetees comme telles: ce n'est pas casse, mais ca merite un
traitement visuel coherent plutot que le traitement actuel au cas par cas.

Aucune vulnerabilite critique ou haute n'a ete trouvee. Les points de securite
identifies (cle de chiffrement unique, executeur sandbox sans isolation par
defaut, sessions de 30 jours sans expiration glissante) sont deja
autoidentifies dans `GOAL.md` comme du "hardening en cours" — cet audit les
confirme avec des references de code precises plutot que de les decouvrir.

## 2. Cartographie actuelle de l'architecture

```
seshat-ui (Electron/React)
    │  HTTP only, 100% local — confirme, aucun appel direct a seshat-server
    ▼
seshat-backend (Go, port 8090)
    │  internal/<domain>  → logique locale mono-utilisateur
    │  internal/cloud*    → 13 adaptateurs optionnels, actifs seulement
    │                        si le serveur cloud repond (voir finding #1)
    ▼ (optionnel, degrade proprement si absent)
seshat-server (Go, port 8081) ─── seshat-console (admin web, React/antd)
    │  internal/server/<domain> → IAM, automation, knowledge, memories,
    │                              quotas, mcpregistry, skillregistry, ...
    ▼
seshat (module Go externe github.com/KPO-Tech/seshat)
    → runtime agent: sandbox bash/browser/fs, MCP client, RAG, providers
```

Points confirmes par l'audit:

- La regle "seshat-backend → seshat/pkg/* seulement, jamais seshat/internal/*"
  (AGENTS.md) est respectee dans le code observe.
- `seshat-ui` est bien un pur consommateur HTTP du backend local — aucune
  logique metier cote Electron/React, aucun appel direct a `seshat-server`.
- Les 13 paquets `cloud*` (`cloudidentity`, `cloudsettings`, `cloudpreferences`,
  `cloudmemories`, `cloudquotas`, `cloudlongterm`, `cloudknowledge`,
  `cloudwebsearch`, `cloudmcp`, `cloudagents`, `cloudautomation`,
  `cloudskillregistry`, `cloudhttp`) sont tous reellement cables dans
  `internal/config/bootstrap.go` et `internal/app.go`, et tous degradent
  proprement vers un fournisseur local quand le serveur n'est pas joignable.
  C'est la partie la mieux concue de toute l'architecture.
- `docs/architecture.md` est **perime**: il decrit `seshat-server` comme un
  "bootstrap" naissant qui "ne possede rien encore" et qui reutilise des
  paquets `seshat-backend` temporairement. Le code reel montre un
  `seshat-server` mature: `iam` a lui seul fait ~10 700 lignes avec 26
  fichiers de tests, `automation` ~4 000 lignes avec 9 fichiers de tests.
  `ROADMAP.md` (2026-07-14) est la source a jour; `docs/architecture.md` doit
  etre corrige (voir section 7).

Maturite reelle des domaines `seshat-server` (lignes de code / fichiers de
tests observes):

| Domaine | Maturite | Note |
|---|---|---|
| `iam` | Mature, teste en profondeur | ~10 700 lignes, 26 fichiers de tests |
| `automation` | Mature, teste en profondeur | ~4 000 lignes, 9 fichiers de tests |
| `knowledge` | Construit, teste | ~2 400 lignes, 6 fichiers de tests |
| `websearchsettings`, `mcpregistry`, `agentregistry`, `preferences`, `skillregistry`, `longtermmemory` | Construit, CRUD fin, peu teste | 1 fichier de test chacun |
| `quotas` | Construit, compteurs seulement | conforme a ce que ROADMAP.md annonce |
| `workspacechat` | Fonctionnel mais **zero test dedie** | reutilise `sdk.Client`/`sdk.Session` en direct — profondeur fonctionnelle non couverte par des tests |
| `mailer` | Utilitaire, zero test | risque faible (SMTP send simple) |

## 4. Doublons a supprimer ou fusionner

### Backend (`seshat-backend`)

- **Reglages utilisateur (P1)**: unifier `PUT /users/me/settings`
  (`internal/api/users.go:209-234`, blob JSON sur `db.User.Settings`) et
  `PUT /users/me/preferences` (`internal/preferences`, modele type).
  Recommandation: garder `preferences` comme source unique typee, migrer les
  cles utilisees de `settings` vers des champs `preferences` explicites, puis
  retirer la colonne `Settings`.
- **Memoire (P1)**: `internal/db/user_memories.go` (table `user_memories`)
  vs `internal/db/memories.go` (`memory_entities`/`memory_observations`/
  `memory_relations`, alimente par l'extracteur long-terme du SDK). Aucune
  vue unifiee aujourd'hui — un utilisateur qui demande "que sais-tu de moi"
  obtient une reponse partielle selon la table interrogee. Recommandation:
  soit fusionner en un seul modele (le graphe est strictement plus riche),
  soit documenter explicitement pourquoi les deux coexistent (ex: memoire
  "manuelle" vs "extraite automatiquement") et exposer les deux dans une
  seule API de lecture cote agent.
- ~~**Permissions (P1)**~~ **[corrige 2026-08-10 — pas un doublon a fusionner]**:
  `requireScopedPermission` (`internal/api/permissions_authz.go:12-22`,
  bypass en mode local) et `requireRole` (`internal/api/auth.go:222-235`,
  jamais de bypass) coexistent deliberement pour deux besoins differents, pas
  par accident. `routes.go:66-67,169` utilise `requireRole("admin", ...)`
  pour `/skills/repos` (installer un depot de skills execute du contenu git
  arbitraire que l'agent suit ensuite — frontiere de securite voulue en tout
  mode) et `/auth/admin/ping` (endpoint de diagnostic dont le seul but est de
  tester ce garde-fou de role, voir `TestAdminEndpointRejectsNonAdminUser`
  dans `api_test.go`). Tentative de migration vers `requireScopedPermission`
  faite puis annulee : elle casse `TestSkillReposRequireAdmin`, qui pin ce
  403 comme une exigence, pas un oubli. Aucun changement necessaire.
- **Schema `seshat-backend` / `seshat-server` (P2)**: `Corpus`, `CorpusFile`,
  `KnowledgeIngestionJob`, `UserMemory`, `MemoryEntity/Observation/Relation`,
  `UsageCounter` sont recopies champ par champ cote `seshat-server`
  (commentaires explicites "mirrors seshat-backend's own ... field-for-field"
  dans `seshat-server/internal/server/db/models.go`). Volontaire et
  documente, mais sans generation partagee ni test croise garantissant que
  les deux schemas restent synchronises. Recommandation: a minima, un test
  d'integration qui compare les deux definitions de structs et echoue si
  elles divergent silencieusement.

### Frontend (`seshat-ui`)

- **Etat de chargement/erreur/vide/toast (P1)**: reimplemente independamment
  dans `pages/workspace/index.tsx`, `pages/settings/AdminViews.tsx`,
  `pages/knowledge/index.tsx`, `pages/inbox/index.tsx`,
  `pages/skills-creator/index.tsx`, `pages/scheduling/index.tsx`, chacun avec
  ses propres classes CSS prefixees (`wk-`, `k-`, `ib-`, `sch-`, `sc-`,
  `adm-`, `project-`, `apps-`). Un seul `EmptyState` local existe
  (`skills-creator/index.tsx:998`) et n'est pas reutilise ailleurs.
  Recommandation: extraire `<PageHeader/>`, `<EmptyState/>`, `<ListState/>`
  (loading/error/empty) et un hook `useAsyncResource` partages dans
  `src/renderer/components/` et `src/renderer/hooks/`.
- **Deux surfaces de gestion des agents**: `pages/workspace/index.tsx`
  (~3000 lignes) est montee a la fois en page autonome (`/workspace`) et
  embarquee dans l'Admin Console (`pages/admin/index.tsx:176-178`, mode
  `embedded`). Ce n'est pas un vrai doublon de code (un seul fichier) mais un
  risque de rayon d'impact: toute modification de cette page affecte
  simultanement l'usage local et l'usage admin/organisation.
  Recommandation: extraire la logique metier (chargement agents/outils) dans
  un hook partage et separer clairement les sous-composants de presentation
  "locale" vs "organisation" pour reduire le couplage.
- **Vues Admin dupliquees via deux points d'entree**: `AdminUsersView`,
  `AdminGroupsView`, `AdminAuditView`, `AdminQuotasView`
  (`pages/settings/AdminViews.tsx`) sont consommees a la fois depuis

  `pages/settings/SettingsNav.tsx` (`admin-users`, `admin-organizations`,
  etc., inatteignables mais toujours dans le type `TabId`).
  Recommandation: retirer ces entrees mortes du type `TabId`.

- Le CRM/prospection (`prospecting`) devrait etre tranche comme une

proprietaires de `seshat-backend`; `docs/architecture.md` l'exprime deja
clairement ("`seshat-server` must never store thread or message bodies
itself") — bonne regle, a laisser telle quelle une fois cette doc corrigee.
