# Audit n8n → consolidation Automation/dataflow (2026-09-04)

> Recadrage produit, 2026-09-06 : ce document n'est pas la roadmap produit d'Agent Workflows et ne doit pas être lu comme une décision de construire un clone de n8n. Il reste une référence technique pour consolider le socle visuel et le moteur d'exécution : triggers comme nodes, webhooks, traces, expressions, pinned data, validation, replay, rétention et robustesse. La direction produit vit maintenant dans `docs/produits/platforms/automation/agent-workflows.md` : Seshat orchestre des agents métier gouvernés qui utilisent outils, plateformes et connaissance pour produire un résultat auditable et mesurable.

Comparaison complète du moteur `pkg/dataflow` + éditeur Automation (`seshat-server`/`seshat-backend`/`seshat-ui`) contre le code réel de `n8n` (clone shallow étudié dans le scratchpad, jamais importé dans ce repo — commit `441970b2`, "n8n 2.37.0"). Objectif de l'utilisateur : ne rien laisser de côté, lister tout, puis traiter un par un, proprement, dans l'ordre.

**Méthode** : 4 agents de recherche en parallèle, chacun scopé sur un domaine (moteur/nœuds, scheduling/webhooks/queue, frontend éditeur, plateforme/entreprise), consigne stricte de citer le code réel lu (fichiers/types), pas de connaissance générique sur n8n. Le catalogue des ~400 intégrations n8n n'a pas été re-comparé (déjà couvert par l'initiative connecteurs des 4 batches, terminée le 2026-09-03) — ce document couvre l'**architecture et l'UX**, pas la liste de services.

**Déclencheur direct** : discussion avec l'utilisateur sur la place d'"Agent/Provider/Model" et du "cron" dans Job settings — sa lecture (trigger-en-tant-que-nœud, provider/modèle par nœud `agent`) est confirmée alignée avec l'architecture réelle de n8n (voir Tier 1, item 1). Bonne nouvelle trouvée en creusant : **n8n lui-même ne combine pas plusieurs triggers avec AND/OR** — chaque nœud trigger démarre sa propre exécution indépendante, point de départ unique. Le vrai besoin est donc "plusieurs points d'entrée indépendants par graphe", pas un moteur de combinaison logique de triggers — plus simple que ce qu'on imaginait.

## Tier 1 — Fondations (à faire en premier, tout le reste en dépend) — [x] Tier entièrement terminé (2026-09-05)

### 1.1 [x] Fait (2026-09-05, Schedule Trigger seulement — Webhook/Poll restent 1.2/1.3) — trigger-en-tant-que-nœud
**Ce que fait n8n** : un nœud a un `.trigger`/`.poll`/`.webhook` implémenté sur son `INodeType` (pas un flag `group`, qui n'est que la catégorisation UI de la palette — `packages/workflow/src/workflow.ts`, `getTriggerNodes()`/`getPollNodes()`). `ActiveWorkflowTriggers.addAllTriggers` active **chaque** trigger/poll du graphe indépendamment ; un graphe à plusieurs triggers a plusieurs points d'entrée indépendants, chacun démarre sa propre exécution avec lui-même comme seul nœud de départ. Pas de AND/OR.
**Pourquoi c'est fondamental** : ça unifie enfin Scheduling (cron/interval/once en colonnes DB) et les règles Inbox event-triggered (`InboxWorkflowStore`, jamais exposées en REST) — le vrai problème documenté depuis plusieurs sessions.
**Scope estimé** : gros — nouveaux types de nœuds trigger dans `pkg/dataflow` (Schedule, Webhook, Poll générique), le scheduler doit lire le graphe pour en dériver le planning au lieu d'interroger seulement des colonnes, l'éditeur perd sa notion de "Job settings = trigger" et gagne des nœuds trigger sur le canevas.
**Dépend de** : rien, mais bloque une bonne partie du Tier 2/3 (le "Run now" par nœud, la validation de graphe, etc. changent de sens une fois qu'un trigger est un nœud).
**Fait, scope Schedule Trigger uniquement** : `pkg/dataflow.NodeDescription.IsTrigger` + nouveau nœud `schedule_trigger` (cron/interval/once) côté SDK ([PR seshat#268](https://github.com/KPO-Tech/seshat/pull/268), pas encore mergée/taguée — `seshat-server/go.mod` porte un `replace` temporaire en attendant). `normalizeJobTrigger` (`seshat-server`) dérive `trigger_type`/`cron_expr`/`interval_seconds`/`run_at` du nœud trigger du graphe au lieu de champs séparés — zéro changement du scheduler lui-même, rétrocompatible par construction (un graphe sans nœud trigger retombe sur le comportement d'avant, aucune migration nécessaire). Côté éditeur : le nœud trigger n'a pas de port d'entrée (forme arrondie à gauche), la section Trigger a disparu de Job settings, et un ancien job sans nœud trigger se voit synthétiser automatiquement un nœud à l'ouverture (côté client, jamais persisté tant que non sauvegardé). Webhook trigger (1.2), Poll trigger générique, et la combinaison multi-trigger restent non commencés.

### 1.2 [x] Fait (2026-09-05, chemin statique par token, pas de dynamique/test-prod) — Webhook trigger
**Ce que fait n8n** : `WebhookEntity` (table dédiée) avec `(webhookPath, method)` en clé primaire → empêche toute collision de route entre workflows, y compris multi-instance. Route dynamique résolue via `pickMatchingTemplate` (match le plus spécifique d'abord). **Test vs Production** sont deux chemins de code séparés : `TestWebhooks` (enregistrement en mémoire, timeout, auto-teardown après un appel, coordination pubsub multi-instance) vs `live-webhooks.ts` (lignes DB persistantes).
**Pourquoi** : aujourd'hui, rien ne peut démarrer un workflow depuis l'extérieur via HTTP. C'est une brique manquante complète, pas une amélioration.
**Scope estimé** : gros. Nouvelle table (équivalent `WebhookEntity`), routage dynamique côté `seshat-server`, distinction test/prod côté éditeur (URL de test affichée pendant qu'on construit, URL de prod une fois activé).
**Fait, scope volontairement réduit** : nouveau nœud `webhook_trigger` côté SDK (`IsTrigger: true`, une propriété `method`), même modèle que `schedule_trigger`. Côté `seshat-server` : chemin statique par token aléatoire (`sdb.NewToken`, 192 bits) au lieu du path dynamique/`pickMatchingTemplate` de n8n — un webhook = `POST /api/v1/webhooks/{token}`, généré une fois à la sauvegarde du job et stable ensuite (jamais régénéré tant que le nœud reste sur le graphe ; révoqué si retiré). Pas de distinction Test/Production — le token n'existe qu'une fois le job sauvegardé, donc pas de fenêtre "test" à gérer séparément. Toujours asynchrone : la requête met en file (`queueRunForJob`) et répond `202` immédiatement, pas de mode "attendre la sortie du graphe" (n8n le propose, pas nous — un futur pass séparé). Fonctionne pour Cloud et Device de la même façon (les deux étaient déjà async). Un graphe peut avoir un `schedule_trigger` ET un `webhook_trigger` en même temps, chacun un point d'entrée indépendant (conforme au constat n8n du haut de ce document). Effet de bord utile trouvé en creusant : **aucun run, avant ce pass, ne pouvait recevoir de payload externe** (le seed était toujours `{job_id, owner_id, organization_id}` fixe) — ajout d'un `JobRun.TriggerPayload` générique (JSON, vide sauf pour un run déclenché par webhook) fusionné dans le seed sous une clé `"webhook"`. **Le vrai manque derrière "pas de Test/Production" comblé séparément** : n8n's split existe pour voir un payload réel pendant qu'on construit — on n'avait aucun équivalent. Plutôt que de répliquer son infra (enregistrement en mémoire, auto-teardown, pubsub multi-instance, inutile ici puisque l'URL est déjà live dès la sauvegarde du job), le nœud `webhook_trigger` affiche maintenant le dernier payload réellement reçu (poll de `GET .../runs` toutes les ~4s côté éditeur, `Run.TriggerPayload` exposé côté serveur — zéro nouvelle route). Volontairement passif : pas de bouton "envoyer un appel simulé", l'intérêt est de voir ce qu'un vrai appelant envoie. **Réponse synchrone comblée aussi** : `responseMode` sur `webhook_trigger` (`immediate` par défaut, inchangé ; `whenFinished`). En mode `whenFinished`, `TriggerJobByWebhook` court-circuite `Scheduler.tick()` (jusqu'à ~30s de latence normalement) — met en file comme d'habitude puis exécute immédiatement dans une goroutine détachée de la requête HTTP entrante (`context.WithoutCancel`), attend jusqu'à 55s (`Service.webhookSyncTimeout`) le résultat réel, et si ça dépasse, répond `504` avec le `run_id` sans annuler l'exécution en arrière-plan. Cloud uniquement — rejeté à la sauvegarde pour un job ciblant un device (aucune borne sur quand un device se connectera). Les trois manques de la version initiale sont maintenant tous comblés, chacun à sa mesure (pas de réplication brute de l'infra n8n). Poll trigger générique reste non commencé.

### 1.3 [x] Fait (2026-09-05, provenance par item sans toucher à `NodeExecutor`) — Granularité d'exécution par nœud (item-level, pas juste succès/échec)
**Ce que fait n8n** : `ITaskData` porte `data`/`inputOverride` typés `ITaskDataConnections` — un tableau `INodeExecutionData[]` **par entrée, par item**, pas juste une sortie agrégée — plus `source` (quel nœud/port amont a alimenté quoi). C'est la fondation technique de tout le Tier 2 (pinned data, dirty-node, replay interactif).
**Pourquoi** : notre `NodeTrace`/`NodeResult` actuel (Success/Skipped/Output/Error/Duration) est déjà un bon début (chantier "historique par nœud" du 2026-09-03) mais reste un enregistrement plat par nœud, pas par item/par port. Sans cette granularité, pinned data et le replay interactif (Tier 2) ne sont pas construisibles proprement.
**Scope estimé initialement** : moyen-gros, touche `pkg/dataflow` (le moteur d'exécution doit capturer cette granularité) avant même l'UI. **Révisé en creusant** : le vrai système n8n (`pairedItem` avec heuristique de secours moteur, `source` par port d'entrée, schéma d'exécution versionné) est plus lourd que "moyen-gros" ne le suggérait — le répliquer aurait cassé la signature `Execute()` de chaque type de nœud.
**Fait, sans breaking change** : la provenance se perdait à deux endroits précis dans la boucle de scheduling de `Run()` elle-même (`pendingInputs[...] = append(...)`, jamais dans le `Execute()` d'un nœud) — un suivi en parallèle (`pendingSources`, même verrou) donne `NodeResult.Input`/`InputSource` (ce qu'un nœud a reçu, et de quel nœud/port amont) et `OutputByPort` (la vraie répartition par port, perdue avant même que `NodeResult` existe) **sans toucher à l'interface `NodeExecutor`** — aucun nœud existant ou futur n'est affecté. `NodeTraceEntry` (seshat-server) mirroré à l'identique. Aucune UI dans ce pass — le doc lui-même le cadre "avant même l'UI" ; un vrai consommateur (pinned data, replay) et ses besoins réels appartiennent au Tier 2. Pas d'inférence `pairedItem` (item de sortie ↔ item d'entrée précis) — différée à Tier 2 quand le replay en aura vraiment besoin, plutôt que construite maintenant sans consommateur.

### 1.4 [x] Fait (2026-09-05, âge + nombre par job, purge simple) — Rétention/purge des données d'exécution
**Ce que fait n8n** : politique complète et configurable — âge max (`EXECUTIONS_DATA_MAX_AGE`, 14j par défaut), nombre max (`EXECUTIONS_DATA_PRUNE_MAX_COUNT`, 10000 par défaut), sauvegarde sélective par issue (`_SAVE_ON_ERROR`/`_ON_SUCCESS`/`_ON_PROGRESS`/`_SAVE_MANUAL_EXECUTIONS`, chacun configurable), purge en deux temps (soft-delete puis hard-delete après un buffer d'1h).
**Pourquoi maintenant** : on garde tout indéfiniment aujourd'hui — pas grave à faible volume, mais on est sur le point d'augmenter fortement le volume de données par run (item 1.3) et le nombre de workflows (item 1.1/1.2 ouvrent la porte à plus d'usage). Autant le faire avant que ce soit un problème plutôt qu'après.
**Scope estimé** : petit-moyen. Un sous-ensemble (âge + nombre max, purge simple) suffit largement pour commencer, pas besoin de répliquer les 6 niveaux de granularité de n8n dès le départ.
**Fait, sous-ensemble volontaire** : deux critères indépendants, chacun désactivable à 0 — âge max global (`SESHAT_SERVER_JOB_RUN_MAX_AGE`, 336h par défaut, comme n8n) et nombre max **par job** (`SESHAT_SERVER_JOB_RUN_MAX_COUNT_PER_JOB`, 10000 par défaut) plutôt que global comme n8n — plus juste entre organisations vu qu'on est multi-tenant, et évite qu'une org très active ne consomme la rétention d'une autre. Jamais un run en cours (`queued`/`claimed`/`running`) n'est purgé, quel que soit son âge. Pas de soft-delete/hard-delete en deux temps (chez n8n ça sert à garder une exécution manuelle visible/annulable brièvement dans l'UI avant suppression réelle — rien chez nous ne lit `JobRun` de façon à avoir besoin de cette fenêtre) ni des 4 indicateurs `_SAVE_ON_*` (chez n8n ils existent parce que la ligne d'exécution doit être créée avant de connaître l'issue pour renvoyer un ID immédiatement — on le fait déjà depuis toujours via `queueRunForJob`, sans avoir besoin d'un indicateur "ne pas garder les succès" séparé). Nouveau type `automation.JobRunPurge`, calqué exactement sur `workspacechat.Cleanup`/`iam.MembershipExpiry` (déjà le bon patron dans ce code, un ticker indépendant du `Scheduler`, pas une étape de plus dans `tick()`) — suppressions par lots (IDs trouvés puis `DELETE ... WHERE id IN (...)`, même idiome GORM que `purgeExpiredSessions`), sans fonction fenêtrée ni réglages de lot par dialecte SQL (complexité propre à n8n, pas fondamentale au besoin).

## Tier 2 — Éditeur utilisable à l'échelle (une fois le Tier 1 posé)

### 2.1 [x] Fait (2026-09-05, `$node`/`$now`/`$today`/`$itemIndex`, pas de `$prevNode` ni d'extensions de méthodes) — Moteur d'expressions (`{{ }}`)
**Ce que fait n8n** : `WorkflowDataProxy` construit un contexte JS enrichi — `$json`, `$now`/`$today` (Luxon), `$parameter`, `$node`, `$prevNode`, `$runIndex`/`$itemIndex`, et surtout **`$('NodeName')`** qui permet d'adresser explicitement n'importe quel nœud en amont (`.item`, `.all()`, `.itemMatching(idx)`) pour du data-linking cross-node — pas juste "la sortie du nœud précédent". Plus des extensions de méthodes sur string/array/date/number utilisables uniquement dans une expression. Point clé trouvé en creusant : cette résolution n'est ni universelle-automatique ni câblée dans l'interface d'exécution — chaque type de nœud appelle la **même** fonction générique `getNodeParameter(name, itemIndex)` pour lire ses propres paramètres ; `If`/`Filter` n'ont rien de spécial, ils appellent exactement la fonction générique que `HttpRequest`/`Set` appellent aussi.
**Pourquoi** : nos nœuds `filter`/`if`/`switch` utilisent déjà goja (JS pur), mais sans cette couche d'ergonomie (`$node`, adressage cross-node), câbler des données entre nœuds éloignés dans le graphe reste pénible/fragile. C'est aussi le prérequis direct de 2.2/2.3 côté UI (l'éditeur d'expression n'a de sens que si le moteur derrière existe).
**Scope estimé** : moyen. Peut se construire sur goja déjà en place, sans nouvelle dépendance lourde.
**Fait, sans changer la signature de `NodeExecutor.Execute()`** : le constat ci-dessus se traduit directement en Go — `Runtime` gagne un `Expr ExpressionEvaluator` optionnel (nil = désactivé, aucun appelant existant n'est affecté) plus une carte interne (verrou dédié) de la sortie de chaque nœud déjà terminé, peuplée par `Run()` lui-même au moment exact où il écrit déjà `result.Results[node.ID]` — donc `$node('Name')` ne voit jamais un nœud qui n'a pas *réellement* fini, comme chez n8n. Deux nouvelles fonctions exportées, `dataflow.ResolveValue`/`ResolveParam`, reprennent la convention `=`-préfixe déjà utilisée par `set` : n'importe quel type de nœud peut les appeler depuis son propre `Execute()` au lieu de lire un paramètre brut, pour obtenir `$json`/`$itemIndex`/`$now`/`$today`/`$node(name)` sans rien changer à l'interface. `http_request` (le cas le plus demandé — câbler la sortie d'un nœud amont dans l'URL/le corps/les headers d'un appel HTTP) les adopte pour `url`/`body`/`headers`. `set` remplace son ancien code `=`-préfixe fait main par `ResolveParam`, avec repli sur son propre pool si un appelant n'a pas encore branché `Runtime.Expr` (zéro régression pour l'existant, notamment le graphe `seshat-backend`/Inbox qui ne branche pas encore `Expr`). `filter`/`if`/`switch` gardent leur convention "le champ entier est du JS", juste enrichie des mêmes nouvelles bindings. **Volontairement absent** : `$prevNode` (nécessiterait de connaître la provenance par item d'un nœud *pendant* son appel, pas après comme le fait déjà `NodeResult.InputSource` du 1.3 — `$node('Name')` couvre le vrai besoin) et les ~111 extensions de méthodes string/array/date/number de n8n (à faire en fonction de l'usage réel, pas par anticipation). Câblé côté `seshat-server` : le pool déjà construit pour `filter`/`if`/`switch`/`set` (auparavant jeté après l'enregistrement) est maintenant aussi donné à `automation.Service` via `SetExpressionEvaluator`, threadé jusqu'au `Runtime` de chaque run cloud. SDK publié en v1.2.32.

### 2.2 [x] Fait (2026-09-05, menu d'insertion + aperçu inline, pas de CodeMirror) — Éditeur d'expression avec autocomplétion + aperçu live (frontend)
**Ce que fait n8n** : intégration CodeMirror 6 réelle (`useExpressionEditor.ts`) — autocomplétion contextuelle (`$json`, `$node`, `$vars`, méthodes par type de donnée), coloration syntaxique inline des segments `{{ }}`, et une popover qui montre la **valeur réellement résolue** contre de vraies données amont, avec un sélecteur pour naviguer entre les items d'entrée.
**Pourquoi** : sans ça, le moteur d'expression (2.1) reste un langage que l'utilisateur tape à l'aveugle dans un textarea JSON — exactement le genre d'UX qu'on a déjà remplacée pour les autres champs (`ParameterForm.tsx`) mais pas encore pour ça.
**Dépend de** : 2.1.
**Scope estimé** : gros côté frontend (CodeMirror 6, complétions custom) — le plus gros chantier UI de ce document après le canevas de trigger.
**Fait, scope volontairement réduit** : le moteur d'évaluation de `pkg/dataflow` est Go/goja, pas du JS isomorphe comme `n8n-workflow` — l'approche 100% client-side de n8n ne se transpose pas telle quelle, et CodeMirror (modules de complétion dédiés, coloration `{{ }}` inline, worker TypeScript pour le Code node) est explicitement le plus gros chantier du document. Coupe nette : pas de CodeMirror, pas de nouvelle dépendance, le `<textarea>`/`<input>` existant de `ParameterForm.tsx` reste tel quel. Deux ajouts à la place, tous deux **toujours visibles** (jamais cachés derrière un clic — préférence déjà établie dans ce code, voir `AgentPickerField`/`SecretRefField`) : une rangée de "puces" cliquables (`$json`, `$itemIndex`, `$now`, `$today`, un `$node('id')` par nœud du graphe) insérées au curseur — l'équivalent de l'autocomplétion de n8n (montrer ce qui existe) via un mécanisme plus simple (menu au clic, pas de complétion en temps réel) ; et, une fois un champ reconnu comme expression (préfixe `=`, ou le champ `expression` toujours-JS de `filter`/`if`), un panneau "Preview result" inline (pas une popover flottante) qui résout la vraie valeur via un nouvel endpoint `seshat-server` (`POST /dataflow/preview-expression`, zéro changement SDK — `Runtime.Expr`/`NodeAccessor` du 2.1 suffisent), pré-rempli avec le vrai dernier `$json` reçu par ce nœud (`JobRun.NodeTrace[...].Input`, Tier 1.3) quand un run existe. `$node(...)` s'aperçoit vide dans ce pass (aucun nœud amont "terminé" pendant un aperçu) — combler ça demanderait de threader la donnée de tous les autres nœuds, différé. Types `json` (headers, cases/casesOrder) explicitement hors scope — pas de traitement par clé dans un blob JSON pour l'instant. Deux bugs préexistants et sans rapport trouvés en testant en vrai : un préfixe d'URL `/automation/...` erroné dans une quinzaine d'appels `api.*` de ce module (dont celui qui empêchait le sélecteur de nœuds de charger quoi que ce soit, et la création de job elle-même) — signalé pour une session dédiée plutôt que corrigé ici (trop large, hors du scope de ce pass) ; et `extractErrorMessage`/`bridgeErrorMessage` qui affichaient "[object Object]" au lieu du vrai message d'erreur serveur (`{"error":{"message":...}}` mal désimbriqué) — corrigé directement ici, un message d'erreur lisible étant au cœur même de cette fonctionnalité (l'aperçu d'une expression invalide).

### 2.3 [x] Fait (2026-09-05, geste identique à n8n, pas de suivi de fraîcheur) — Pinned data (données de test épinglées)
**Ce que fait n8n** : `IPinData = { [nodeName]: INodeExecutionData[] }` — un tableau de sortie simulée par nœud, stocké directement dans le JSON du workflow (pas une table à part), consulté par le moteur avant de vraiment exécuter le nœud. Badge visuel dédié sur la carte du nœud.
**Pourquoi** : permet de construire/tester un graphe sans faire tourner à chaque fois les vrais appels externes (coûteux, lents, parfois destructifs — écrire un vrai ticket Jira à chaque test du nœud suivant).
**Dépend de** : 1.3 (granularité item-level).
**Scope estimé** : moyen.
**Fait, même geste que n8n** : `Definition` gagne `PinnedData map[string][]Item` (clé = ID de nœud, même forme que `IPinData`, gardé séparé des `Parameters` propres à chaque nœud — "sortie de test gelée" est un concept différent de la vraie configuration). `Run` vérifie ça avant même d'appeler l'exécuteur réel d'un nœud — ni son lookup dans le registre, ni `ValidateParameters`, ni `Execute` ne sont jamais atteints pour un nœud épinglé, donc un graphe reste testable avec un nœud dont la config réelle est incomplète, ou dont le type n'existe même pas encore. Les items épinglés deviennent la sortie du port "main" exactement comme si `Execute` les avait vraiment renvoyés : les nœuds en aval les reçoivent comme un vrai `Input`/`InputSource`, et `$node(nom)` (2.1) les voit aussi, sans câblage supplémentaire — épingler ne remplace que l'appel `Execute`, pas le reste de la boucle d'ordonnancement/d'enregistrement autour. Aucun changement backend au-delà du bump SDK : `PinnedData` n'est qu'un champ de plus du même `dataflow.Definition` déjà sérialisé tel quel dans `Job.GraphJSON` — sauvegarder/charger un job avec des données épinglées ne touche à rien côté `seshat-server`. `NodeTraceEntry` gagne `Pinned bool` pour distinguer "ce nœud a vraiment tourné" de "ceci vient de données gelées". Côté éditeur : une case à cocher "Pin output" par nœud (pas par champ, contrairement à 2.2) au-dessus du formulaire de paramètres, un textarea JSON pour les items gelés, un bouton "Use last real output" qui les préremplit depuis le vrai dernier run de ce nœud (réutilise le même mécanisme que l'aperçu d'expression du 2.2 — extrait dans un module `runHistory.ts` partagé plutôt que dupliqué), et un badge visuel sur la carte du nœud dans le canevas. **Volontairement absent** : le suivi de fraîcheur "les données épinglées deviennent obsolètes quand les paramètres changent" — c'est le 2.4, plus gros, et un pin ici est juste "actif" ou "inactif", à retirer manuellement. Vérifié en vrai : bascule/éditeur JSON/badge fonctionnent dans l'éditeur, et `pinned_data` survit à un vrai cycle création → rechargement de job contre un `seshat-server` de test (SDK v1.2.33).

### 2.4 [x] Fait (2026-09-07, un seul booléen de fraîcheur au lieu des 4 raisons de n8n) — Exécution manuelle par nœud + suivi de "dirtiness"
**Ce que fait n8n** : bouton "tester ce nœud" au survol de chaque carte, animation de bordure pendant l'exécution live (`.running` + animation CSS), et surtout un vrai suivi de **fraîcheur** (`CanvasNodeDirtiness`: `parameters-updated`/`incoming-connections-updated`/`pinned-data-updated`/`upstream-dirty`) — un badge indique quand la dernière exécution d'un nœud est devenue obsolète par rapport aux modifications faites depuis.
**Pourquoi** : aujourd'hui, "Run now" n'existe que depuis Scheduling sur un job déjà sauvegardé (item explicitement noté manquant le 2026-09-03) — ceci va plus loin et le rend utile nœud par nœud pendant la construction.
**Dépend de** : 1.3.
**Scope estimé** : moyen-gros (logique de dirtiness non triviale à porter correctement).
**Bloqueur réel trouvé en creusant, hors scope de ce fix** : `automation/index.tsx` ne renseigne jamais `organization_id` en créant/modifiant un job, alors que `CreateJob`/`UpdateJob` le rejettent sans (`ErrInvalidInput`) — la création de job semble cassée de bout en bout contre un vrai `seshat-server` multi-tenant, pas juste un artefact d'environnement de test. Signalé séparément plutôt que corrigé ici. **Contournement adopté pour ce pass** : "tester ce nœud" n'apparaît qu'une fois le job déjà sauvegardé au moins une fois (`jobId` présent), exactement la même précondition que "Run now" a déjà depuis Scheduling — l'`organization_id`, lui, se lit sur la réponse `GET /jobs/{id}` (déjà renvoyé par le serveur, juste pas encore gardé côté client).
**Fait, sans changement SDK** : `dataflow.Run` fait déjà tout ce qu'il faut — le seul ajout est une façon ad hoc et sans état de l'appeler, via `automation.Service.TestRunGraph` (nouveau, réutilise exactement le câblage `Secrets`/`Expr` qu'un vrai run construit déjà, moins `Agent`/`Subworkflow` qui ont besoin d'une vraie `sdk.Session` — hors scope ici, un nœud `agent`/`subworkflow` dans la chaîne testée échoue proprement à ce nœud précis, comme n'importe quel autre nœud mal configuré). Ne crée jamais de ligne `JobRun`/`NodeTrace`, ne touche jamais à la file d'attente. Nouvel endpoint `POST /dataflow/test-run`. Côté éditeur : "tester ce nœud" calcule la fermeture transitive des ancêtres du nœud cliqué (`ancestorClosure`, simple BFS arrière sur les arêtes déjà en mémoire côté client) et l'envoie telle quelle — tester un nœud en aval rejoue donc sa vraie chaîne amont (épingler les nœuds coûteux en amont — 2.3 — pour éviter de les refaire tourner pour de vrai). **Fraîcheur, réduite à un seul booléen** au lieu des 4 raisons de `CanvasNodeDirtiness` : la fraîcheur d'un nœud, c'est exactement "renvoyer la même fermeture d'ancêtres produirait-elle le même JSON qu'au moment du test" — un paramètre modifié, une connexion changée ou un pin modifié n'importe où dans la chaîne amont changent tous cette sérialisation, donc cette seule comparaison couvre les 4 cas de n8n sans taxonomie dédiée. Piège trouvé en vérifiant en direct : la fermeture propre à CHAQUE nœud (pas celle du nœud cible) doit servir de base à son propre instantané de fraîcheur — un nœud amont a une fermeture plus petite qu'un nœud cible en aval, donc partager un seul instantané entre tous les nœuds testés ensemble faisait apparaître les ancêtres comme obsolètes immédiatement après un test pourtant réussi (corrigé avant de committer). Badge visuel sur la carte (coin bas-droit, symétrique du badge de pin du 2.3 en haut-droit) : pulsation pendant l'exécution, vert si frais, gris atténué si obsolète, rouge en erreur. Vérifié en direct de bout en bout contre un `seshat-server` de test : tester un vrai enchaînement `http_request` → `set` déclenche un vrai appel HTTP et montre le vrai résultat ; modifier l'URL du nœud `http_request` assombrit immédiatement son badge en "obsolète" sans autre clic ; épingler sa sortie puis retester montre la donnée épinglée sans aucun appel HTTP réel (`duration: 0`, `NodeResult.Pinned: true`).

### 2.5 [x] Fait (2026-09-07, vérification de champs requis uniquement, 100% frontend) — Badges de validation statique sur le canevas
**Ce que fait n8n** : validation des paramètres d'un nœud **avant** toute exécution (champ requis manquant, mal typé...), affichée comme un badge distinct du badge d'erreur d'exécution.
**Pourquoi** : notre `ValidateParameters` existe déjà côté SDK par type de nœud (utilisé en amont d'une exécution) mais n'est jamais utilisé pour donner un retour visuel immédiat sur le canevas pendant la construction.
**Scope estimé** : petit-moyen — la logique de validation existe déjà côté SDK, "juste" à l'exposer visuellement.
**Fait, volontairement réduit à un seul check** : le vrai `ValidateParameters` de n8n (par type de nœud, Go, côté serveur) fait des checks profonds et spécifiques à chaque type (SSRF sur `http_request`, noms de cas croisés sur `switch`...) — les dupliquer côté client aurait créé une seconde couche de validation, forcément divergente de la vraie. Réduit au seul check qui est à la fois le plus courant et entièrement exprimable avec ce que le frontend a déjà sous la main : présence des champs requis, via `NodeProperty.required`/`displayIf` du catalogue de types de nœuds (déjà récupéré pour `ParameterForm`) comparé aux `parameters` déjà stockés sur le nœud. Zéro appel réseau, zéro changement backend/SDK, fonctionne même sur un job jamais sauvegardé. Les checks plus profonds continuent de remonter via "tester ce nœud" (2.4) plutôt que d'être dupliqués ici. Nouveau fichier `validation.ts` (`missingRequiredFields`), badge dédié coin haut-gauche sur `GraphNode.tsx` (le seul coin encore libre — pin en haut-droit du 2.3, statut de test en bas-droit du 2.4 — donc les trois badges peuvent s'afficher simultanément sans jamais se chevaucher), calculé dans le même tableau dérivé `nodesForCanvas` de `GraphEditor.tsx` qui portait déjà `isStale` — recalculé à chaque render, jamais lu par `flowToDefinition`, donc jamais persisté dans le `DataflowDefinition` sauvegardé. Vérifié en direct : un nœud `http_request` avec une URL vide affiche le badge ambre avec l'infobulle "Missing required field: URL" ; remplir l'URL fait disparaître le badge immédiatement (recalculé à chaque render, aucune invalidation explicite nécessaire) ; un type de nœud sans schéma de propriétés (`Set`) n'affiche jamais de faux positif.

### 2.6 [x] Fait (2026-09-07, un seul champ nouveau côté backend, aucun nouvel endpoint) — Replay interactif d'une exécution passée ⭐ (la trouvaille la plus différenciante)
**Ce que fait n8n** : cliquer sur un run passé ne montre pas juste un log plat — ça **remonte le vrai canevas** (même composant que l'éditeur) en lecture seule contre les données figées de ce run précis ; cliquer un nœud ouvre son panneau habituel avec les vraies données d'entrée/sortie de CE run.
**Pourquoi c'est la meilleure trouvaille du rapport** : notre "Activities" (chantier du 2026-09-03) est un log plat par nœud (icône statut/durée/aperçu tronqué) — utile, mais rien à voir avec pouvoir littéralement rejouer visuellement un run sur le graphe réel.
**Dépend de** : 1.3 (sans la granularité item-level, il n'y a pas grand-chose à montrer par nœud lors du replay).
**Scope estimé** : gros — réutilise le composant canevas existant en mode lecture seule + une nouvelle source de données (snapshot du run au lieu du graphe live).
**Constat qui a changé le point de départ** : Automation (l'app graphe séparée de Scheduling plus tôt dans ce chantier) n'avait alors *aucune* UI d'historique de runs pour les jobs graphe — pas même un log plat (son propre commentaire sur `AutomationOverviewPanel` le disait explicitement : "no run-inspector/node-trace drill-down yet... a fast-follow"). Il a donc fallu ajouter à la fois la liste des runs ET le replay canevas, pas juste moderniser une vue existante.
**Fait, un seul champ backend nouveau** : `JobRun.NodeTrace` (déjà là depuis le 1.3/2.3/2.4) associe ses entrées aux nœuds du canevas par ID — sans figer la forme du graphe au moment du run, rejouer un run après une édition du graphe (nœud renommé/ajouté/supprimé) aurait affiché la structure d'aujourd'hui avec les données d'hier mal attribuées. `sdb.JobRun` gagne donc `GraphSnapshot string` (le `GraphJSON` du job exactement tel qu'il était à la mise en file du run), rempli une seule fois dans `queueRunForJob` — le constructeur déjà partagé par le planificateur, "Run now" et le webhook. `automation.Run` expose `graph_snapshot` en `*dataflow.Definition` (même geste que `Job.Graph`, via les helpers `graphFromJSON`/`graphToJSON` déjà là). `GET /jobs/{id}/runs` et `GET /runs/{id}` renvoyaient déjà `node_trace` ; ils renvoient maintenant `graph_snapshot` avec, sans second aller-retour réseau côté frontend. Côté éditeur, trois nouveaux fichiers dédiés (même convention que `TestNodeField.tsx`/`validation.ts`) : `GraphReplayViewer.tsx` (canevas en lecture seule, réutilise `definitionToFlow`/`GRAPH_NODE_TYPES`/le CSS de l'éditeur — maintenant exporté — sans aucune de ses mécaniques de mutation ; associe chaque nœud à son `NodeTraceEntry` et réutilise tel quel le badge `testStatus`/`testResult` du 2.4, même langage visuel, juste une autre source de données, sans nouveau coin de badge), `RunNodeDetailPanel.tsx` (sœur en lecture seule de `ParameterForm`), `RunsPanel.tsx` (liste des runs, un seul chargement, pas de polling — même geste que `runHistory.ts`). `GraphNode.tsx` gagne un statut `'skipped'` (branche if/switch non empruntée). Nouvel item de rail "Runs" dans `automation/index.tsx`, visible une fois le job sauvegardé (même précondition que "tester ce nœud"). Vérifié en direct de bout en bout contre un vrai `seshat-server` : job graphe `schedule_trigger → http_request → set`, deux runs déclenchés, liste des runs correcte, replay du run réussi montrant la forme figée du graphe avec les vrais badges de succès, clic sur un nœud montrant ses vraies entrée/sortie en lecture seule, et un run sans `node_trace` (échec avant même l'exécution du graphe) affichant "Not recorded in this run" plutôt qu'un faux badge.
**Bug réel trouvé en vérifiant, hors scope de ce fix, signalé séparément** : `automation.Service.finishCloudRun` échoue à sérialiser un `NodeTrace` non vide via son `Updates` GORM basé sur une map ("unsupported type db.NodeTraceEntry, a struct") — aucun job graphe dont le dataflow atteint réellement l'exécution ne peut donc aujourd'hui terminer un run pour de vrai sans planter. Aucun test existant n'exerçait ce chemin (le seul test de `finishCloudRun` passe `nil` comme `nodeTrace`) — trouvé en déclenchant un run réel de bout en bout.

## Tier 3 — Complétude plateforme (une fois 1 et 2 posés)

### 3.1 [x] Fait (2026-09-07, SDK v1.2.37) — Retry/erreur par nœud + concept de "Error Workflow"
**Ce que fait n8n** : par nœud, `retryOnFail`/`maxTries` (2-5)/`waitBetweenTries` (0-5000ms) et `onError` (`continueErrorOutput` route les items en échec vers une 2e sortie dédiée / `continueRegularOutput` / `stopWorkflow`). Séparément : un **Error Workflow** — un workflow entier désigné pour tourner automatiquement quand un autre échoue, avec un payload dédié (`execution: {id, url, error, lastNodeExecuted}` ou `trigger: {error}` si l'échec est survenu avant toute exécution sauvée), garde anti-boucle si l'error workflow échoue lui-même.
**Scope estimé** : moyen (retry par nœud) + moyen (error workflow, réutilise le concept de workflow existant).
**Fait** : SDK — `dataflow.Node` gagne `RetryOnFail`/`MaxTries` (clampé 2-5)/`WaitBetweenTriesMS` (clampé 0-5000)/`OnError` (`""` = comportement actuel inchangé / `continueRegularOutput` / `continueErrorOutput`) en siblings de `Parameters`/`Connections`, exactement la forme de `INode` chez n8n (délibérément pas le motif `PinnedData` — retry/erreur est du comportement de prod réel, pas une config de test). `NodeResult` gagne `Attempts` et `Continued` (échoué mais le run continue quand même — distinct de `Success` pour que trace/replay distinguent "a vraiment échoué" de "a échoué mais on a continué", la même distinction que fait n8n). `engine.go` retente via un nouveau helper `executeWithRetry` et route vers un nouveau port `"error"` pour `continueErrorOutput` — les ports de sortie nommés étaient déjà un concept purement piloté par la donnée (`Output.Ports`), donc aucun changement structurel du moteur n'a été nécessaire. Publié en v1.2.37 (PR [#287](https://github.com/KPO-Tech/seshat/pull/287) `dev`, PR [#288](https://github.com/KPO-Tech/seshat/pull/288) `dev→main`) ; 5 nouveaux tests moteur, comportement strictement inchangé quand `RetryOnFail`/`OnError` ne sont pas positionnés (tout graphe sauvé avant cette fonctionnalité). Backend — `ScheduledJob.ErrorWorkflowJobID` (nullable, intégrité côté app comme toute autre référence d'ID sur ce modèle) ; `CreateJob`/`UpdateJob` valident (doit exister dans la même organisation, pas d'auto-référence) via un nouveau `normalizeErrorWorkflowJobID` ; `finishCloudRun`, une fois sa propre transaction validée, déclenche en best-effort l'Error Workflow configuré via `triggerErrorWorkflowIfConfigured` — délibérément hors transaction (un échec à mettre en file l'error workflow ne doit jamais affecter l'enregistrement d'échec déjà commité) et délibérément après le commit (pour ne pas dépendre du bug déjà signalé de sérialisation de `NodeTrace` au 2.6). Garde anti-boucle : le `TriggerPayload` d'un run d'error-workflow est enveloppé sous une clé `"error_trigger"` (contrairement au payload webhook, non enveloppé), donnant à la garde un marqueur non ambigu à vérifier avant de cascader. 5 nouveaux tests côté serveur (validation, déclenchement réel, garde anti-cascade). Frontend — nouveau `RetrySettingsField.tsx` (même forme que `PinnedOutputField`/`TestNodeField`), câblé dans `ParameterForm.tsx`/`GraphEditor.tsx` ; `convert.ts` fait apparaître un port `"error"` sur le canevas quand `onError` vaut `continueErrorOutput` ; le tiroir de réglages d'un job gagne un sélecteur "Error workflow" listant les autres jobs de l'organisation.
**Vérifié** : build/vet/test propres dans les deux dépôts (SDK + seshat-server), 10 nouveaux tests au total tous passants, y compris deux tests serveur qui pilotent le vrai chemin `finishCloudRun → triggerErrorWorkflowIfConfigured → queueRunForJob` contre une vraie DB de test (déclenchement réel + garde anti-cascade). `npm run typecheck`/`npm run lint` propres côté `seshat-ui`. Vérification manuelle en direct dans le navigateur non aboutie cette fois : `seshat-backend` (l'API locale que l'app Electron consomme) reste bloqué au démarrage pendant l'init du query runtime/sandbox dans cet environnement, un problème préexistant sans rapport avec ce chantier — signalé séparément plutôt que corrigé ici.
**Bug réel trouvé en creusant, hors scope, signalé séparément** : `seshat-backend` (`internal/config/bootstrap.go`, `BuildApp`) reste bloqué indéfiniment au démarrage juste après l'init du service RAG, avant d'atteindre `sdk.NewClient`/l'écoute HTTP — reproduit avec un embedder local (`ollama`, hôte injoignable) donc pas un simple timeout réseau lent ; empêche toute vérification manuelle en direct de l'app Electron dans cet environnement tant que la cause exacte n'est pas identifiée.

### 3.2 [x] Fait (2026-09-07, bump SDK v1.2.36 + vrai contexte organisation côté frontend) — Variables
**Ce que fait n8n** : vraie fonctionnalité (pas un stub) — page de réglages dédiée, référencées par `$vars.CLE` dans n'importe quelle expression, avec autocomplétion dédiée.
**Dépend de** : 2.1 (le moteur d'expression doit exister pour que `$vars` ait un sens).
**Scope estimé** : petit-moyen une fois 2.1 posé — c'est notre page "Variables" déjà stubée côté `seshat-ui`, il ne manque que le backend + le branchement expression.
**Constat qui a changé le point de départ** : deux découvertes en creusant. (1) Le moteur d'expression vit dans un dépôt séparé (`github.com/KPO-Tech/seshat`) — deux des trois endroits qui construisent les bindings d'une expression (`ResolveValue`, `logicBindings`) y habitent, donc `$vars` ne pouvait pas être livré correctement sans y toucher (une version frontend/seshat-server seule aurait fonctionné en aperçu mais pas à l'exécution réelle, ou l'inverse). (2) Le frontend n'avait aucune notion d'"organisation courante" indépendante d'un job ouvert — chaque fonctionnalité scopée par organisation jusqu'ici (tester ce nœud, Runs, le panneau webhook) contournait ça en lisant `organization_id` sur un job déjà chargé. Demandé explicitement à l'utilisateur : corriger la racine plutôt que scoper Variables à "utilisable seulement depuis un job ouvert".
**Fait** : SDK — `Runtime` gagne `Vars map[string]string` + un accesseur `VarsMap()` nil-safe (même sûreté que `NodeAccessor`), câblé dans `ResolveValue` et `logicBindings` ; publié en v1.2.36 (PR [#285](https://github.com/KPO-Tech/seshat/pull/285) `dev`, PR [#286](https://github.com/KPO-Tech/seshat/pull/286) `dev→main`). Backend — nouveau package `dataflowvariables` (mirroring quasi exact de `dataflowsecrets`, sans chiffrement puisqu'une Variable n'est pas un secret, avec un vrai `Update` cette fois puisqu'une page de réglages doit permettre de changer une valeur) ; nouvelles permissions `variables.read`/`.manage` ; `automation.Service` gagne un `DataflowVariableResolver`, câblé dans `runGraph` (vrai run) et `TestRunGraph` (test ad hoc) ; `PreviewExpression` prend désormais un principal + `organization_id` et vérifie la permission avant de résoudre `$vars` — poste de sécurité réellement différent d'avant (cet endpoint était jusqu'ici "aucune donnée tenant-scoped"), fait délibérément. Frontend — nouveau `useOrganizationStore` global, alimenté par l'appel `/auth/me` déjà fait par `AuthGuard.tsx` à chaque démarrage de session (le résultat était jusqu'ici juste jeté) ; nouvelle page `VariablesPanel.tsx` (liste/création/édition/suppression), accessible depuis l'Overview d'Automation maintenant que l'organisation ne dépend plus d'un job ouvert ; puces d'insertion `$vars.NOM` dans `ExpressionField.tsx`. Corrigés au passage, cause directe d'avoir enfin un id d'organisation à envoyer : la liste des jobs d'Overview et la création de job utilisaient le mauvais préfixe d'URL (`/automation/jobs` au lieu de `/jobs`) et n'envoyaient jamais `organization_id` (ce dernier point explicitement signalé et contourné au 2.4) — les deux marchent maintenant réellement, vérifié en direct.
**Bugs réels trouvés en creusant, hors scope, signalés séparément** : le même bug de préfixe `/automation/` est en fait systémique (`scheduling/index.tsx`, `SecretRefField.tsx`, `WebhookLastCall.tsx`, `settings/CloudAutomationView.tsx`) ; et `useProviders.ts` appelle `/settings/providers` au lieu du vrai `/provider-settings`.
**Vérifié** : en direct de bout en bout (création d'une variable, puce `$vars.API_BASE`, aperçu résolvant la vraie valeur) ; la résolution côté exécution réelle (pas seulement l'aperçu) est prouvée par un nouveau test Go, `TestJobWorkflowRunGraphResolvesVarsForRealExpressions`, qui pilote `runGraph` directement à travers un vrai `dataflow.Run` — le chemin complet par le vrai planificateur bute avant sur le bug déjà signalé de `finishCloudRun` (2.6), donc ce test est la façon honnête de prouver le câblage sans dépendre d'un bug non lié.

### 3.5 [x] Fait (2026-09-09, SDK v1.2.39) — Contrat de test de connexion pour les dataflow secrets
**Ce que fait n8n** : `ICredentialType.test` est une requête HTTP déclarative (endpoint + règles de succès) utilisée par le bouton "Test" dans l'UI ; et un identifiant peut être créé **depuis le formulaire du nœud lui-même** (pas seulement une page de réglages séparée) via `NodeCredentials.vue`.
**Pourquoi** : on a déjà `probeProviderCredential` pour les providers LLM (chantier gouvernance du 2026-08-29) — généraliser le même principe aux connecteurs/secrets dataflow serait cohérent. La création inline depuis le panneau de nœud est un vrai gain UX (pas besoin de quitter le canevas pour aller connecter un compte).
**Scope estimé** : petit (test, motif déjà connu) + moyen (création inline).
**Constat qui a changé le point de départ** : en creusant, il y a en réalité trois surfaces de credentials distinctes, pas une. (1) `DataflowSecret` (nom+valeur opaque, sans notion de "type") consommé par les 4 nœuds base de données (postgres/mysql/sqlite/redis/mongodb/elasticsearch) — la création inline existe **déjà** (`SecretRefField.tsx`, pick-or-create dans le panneau de nœud) ; le seul vrai manque ici est le test. (2) `ConnectorAccount` des ~20 nœuds "envoyer/créer" tiers (Stripe, SendGrid, Jira...) — aucune UI de connexion n'existe pour la plupart de ces comptes, un manque bien plus large que "rendre la création inline" et signalé séparément. (3) Les providers LLM, déjà couverts par `probeProviderCredential`. Le scope a donc été volontairement réduit au test de `DataflowSecret` seul.
**Fait** : SDK — nouvelle interface optionnelle `dataflow.TestableExecutor` (`TestConnection`), l'équivalent Go du fallback `testedBy` de n8n (puisqu'un `DataflowSecret` n'a pas de "type" pour accrocher un `ICredentialType.test` déclaratif dessus) ; `NodeDescription.IsTestable` posé par `Registry.Types()` via une assertion de type, jamais codé en dur par type de nœud ; implémenté pour les 4 nœuds base de données, chacun ne résolvant que son propre secretRef et faisant la vérification réelle la moins chère possible (Ping SQL, PING Redis, Ping Mongo, GET racine Elasticsearch) — donc testable même si le reste des paramètres du nœud (query/operation/key) n'est pas encore rempli. Publié en v1.2.39. Backend — `automation.Service.TestNodeConnection` + `ConnectionTestResult`, un verdict à deux voies (`ok`/message) plutôt que les quatre voies de `probeProviderCredential` : le message d'erreur d'un driver DB explique déjà ce qui cloche, sans avoir les codes HTTP universels (401/403) qui justifient la voie "unknown" côté providers LLM ; `POST /dataflow/test-connection`. Frontend — nouveau `ConnectionTestField.tsx`, affiché quand `isTestable` vient du catalogue de nœuds ; teste la valeur de secretRef **actuellement saisie dans le formulaire**, pas seulement un nœud déjà sauvegardé (même UX "tester avant de sauvegarder" que n8n) — la logique de coercion de `saveForm()` a été extraite dans `buildParamsFromDrafts` pour être réutilisée sans dupliquer le code.
**Vérifié** : build/vet/test propres dans les deux dépôts, 11 nouveaux tests (SDK + service + handler) tous passants, dont un cas de bout en bout réel via un `DataflowSecret` sauvegardé et une vraie connexion SQLite. `npm run typecheck`/`npm run lint` propres côté `seshat-ui`. Vérification manuelle en direct dans le navigateur non refaite cette fois — même limitation que 3.1 (le blocage au démarrage de `seshat-backend`, déjà signalé séparément, toujours pas résolu dans cet environnement).
**Gap réel trouvé en creusant, hors scope, signalé séparément** : aucune UI de connexion n'existe pour la quasi-totalité des `ConnectorAccount` que les ~20 nœuds tiers "envoyer/créer" utilisent (Stripe, SendGrid, Mailgun, Postmark, Telegram, Discord, Trello, Airtable côté statique ; Gmail, Jira, Notion, Salesforce... côté OAuth) — le backend le permet déjà (`CreateStaticAgentAccount`, endpoints génériques), mais `ConnectorsView.tsx` n'expose que 4 kinds au total. C'est un prérequis pour que la Galerie de Templates (3.3) ait un sens sur un modèle qui utilise l'un de ces connecteurs.

### 3.6 Données binaires (fichiers) entre nœuds
**Ce que fait n8n** : jamais de bytes de fichier dans le JSON d'un item — un `BinaryDataService` pluggable (filesystem/S3/Azure) stocke le fichier, l'item ne porte que des métadonnées + un jeton signé (JWT, expiration 24h) pour le récupérer hors-bande.
**Pourquoi** : pas urgent tant qu'aucun nœud ne fait transiter de fichiers (pièces jointes email, exports CSV...) — mais un vrai mur si on ajoute ce genre de nœud sans y avoir pensé avant (tout finirait en mémoire/JSON).
**Scope estimé** : moyen, mais à ne construire que quand un nœud concret en a besoin — pas la peine en spéculatif.

## Tier 4 — Infrastructure de montée en charge (seulement si on tourne à plusieurs instances / fort volume)

### 4.1 Scheduler "durable" (évolution du CAS actuel, pas une réécriture)
**Ce que fait n8n** : notre CAS (`UPDATE ... WHERE next_run_at = ?`) est **exactement le même primitif de base** que l'exécuteur de n8n — validé, pas à jeter. Ce qu'ils ajoutent par-dessus : un vrai bail/reclaim (un job réclamé mais jamais terminé est repris après expiration), une politique de "misfire" (`skip`/`coalesce`/`coalesce_owner` si un déclenchement a été raté), une fenêtre de matérialisation des occurrences futures proches, et une passe de réconciliation. **Fait notable** : n8n n'utilise **pas** d'élection de leader pour ce mécanisme précis (seulement pour d'autres tâches périodiques legacy comme la purge/le renouvellement de licence) — confirme que notre approche est la bonne direction, juste incomplète.
**Scope estimé** : moyen — évolution incrémentale de l'existant, pas une réécriture.

### 4.2 Séparation processus principal / workers (type Bull+Redis)
**Ce que fait n8n** : le processus qui réclame un job n'exécute pas lui-même — il met en queue une référence légère (`{executionId, workflowId, ...}`, pas le payload complet), un pool de workers séparé la traite, et le résultat revient par pubsub.
**Pourquoi pas maintenant** : n'a de sens qu'une fois qu'on tourne à plusieurs instances avec un vrai volume — sinon c'est de la complexité gratuite (nouvelle dépendance Redis, nouveau mode de déploiement).
**Scope estimé** : gros, et à ne déclencher que si la charge réelle le justifie.

## Tier 5 — Entreprise, explicitement mis de côté pour l'instant

Ces éléments existent bien dans n8n (pas des suppositions), mais notre propre lecture — confirmée par la recherche — est qu'aucun n'est un vrai besoin à ce stade du produit. Listés pour ne rien cacher, pas pour être traités maintenant.

- [ ] **SSO/SAML/LDAP/OIDC** — 3 bibliothèques protocolaires distinctes (`samlify`, `ldapts`, `openid-client`) + UI d'admin dédiée. Ne devient pertinent qu'avec des clients dont l'IT exige un login géré par annuaire d'entreprise.
- [ ] **Coffre de secrets externe** (Vault/AWS Secrets Manager/Azure Key Vault/GCP/Infisical/1Password) — mécanisme `$secrets.provider.clé` dans les expressions. Notre couple "coller un secret + chiffrer" suffit tant qu'aucun client n'exige un coffre externe spécifique.
- [ ] **Source control (git)** — sérialisation des workflows/credentials en fichiers JSON + push/pull via `simple-git`. Pertinent seulement pour un usage "workflow-as-code"/GitOps, pas un besoin générique.
- [ ] **API publique versionnée + clés API scopées** — séparée de l'API interne de l'éditeur, avec des scopes propres aux clés (sous-ensemble du modèle RBAC). À faire seulement si on productise une vraie API externe pour des intégrateurs tiers.
- [ ] **Log streaming** (webhook/Syslog/Sentry) — utile seulement une fois que des clients veulent brancher nos événements sur leur propre SIEM.
- [ ] **Insights/analytics** (tableau de bord d'exécutions) — sous-système non trivial (collecte + agrégation périodique + purge dédiée). À ne construire que sur demande client claire.
- [ ] **Mécanisme de licence/feature-gating** — SDK propriétaire + cert signé. On n'a pas de palier commercial à gater aujourd'hui.

**Note positive, pas un gap** : nos audit logs (table persistante, interrogeable) sont en fait **plus utiles out-of-the-box** que ceux de n8n, qui ne persiste rien par défaut (uniquement un bus d'événements + fichier local/streaming externe optionnel). Rien à faire ici.

**À creuser, pas urgent** : le système de permissions de n8n (`Scope = "resource:operation"`, rôles personnalisés par projet) est réellement comparable en sophistication à notre `PolicyBinding` — vaut le coup d'aller lire `packages/@n8n/permissions/src/types.ee.ts` pour des idées le jour où on retravaille le nôtre, mais ce n'est pas un manque actif aujourd'hui.

## Tier 0 — Bugs et lacunes UX confirmés dans le code actuel (2026-09-04)

Suite directe : l'utilisateur soupçonnait que des opérations de base manquaient ("la suppression des nœuds, ...") et a demandé un audit du code réel, pas une comparaison à n8n. Trouvé en lisant directement `seshat-ui/src/renderer/pages/automation/graph/*.tsx` — pas des suppositions, code cité précisément. Ces items passent **avant** le Tier 1 (corrections/petites lacunes sur ce qui existe déjà, pas de nouvelle architecture).

### 0.1 [x] Fait (2026-09-04, `58904ec`) — boutons Delete/Duplicate/Save non stylés (quasi invisibles)
`ParameterForm.tsx` (lignes 169/172/175) et `SecretRefField.tsx` (lignes 94/97) utilisent `className="ib-action-btn"` — une classe qui n'existe **que** dans le `<style>` de la page Inbox (`pages/inbox/index.tsx`), jamais chargée par la page Automation. Résultat : les boutons "Save parameters"/"Duplicate"/"Delete node" (et "Save"/"Cancel" dans le formulaire de création de secret) sont **fonctionnellement câblés** (`onClick` correct, testé en lisant `deleteSelectedNode`/`onNodesDelete`) mais s'affichent en boutons par défaut du navigateur, sans le style du reste de l'éditeur — facile à ne pas remarquer ou à prendre pour un élément cassé/absent. **C'est très probablement l'explication de "je n'arrive pas à supprimer un nœud"** : le bouton existe et marche, mais ne ressemble à rien.
**Fix** : remplacer `ib-action-btn` par une vraie classe scoped à l'éditeur (ex. `.gf-action-btn`), stylée dans `GRAPH_EDITOR_CSS` (déjà chargé sur toute la page). Petit, rapide, à faire en premier.

### 0.2 [x] Fait (2026-09-04, `5f83844`) — renommer un nœud vers un ID déjà pris échoue silencieusement
`GraphEditor.tsx`'s `renameNode()` (ligne 206) fait `if (newId === oldId || nodes.some(n => n.id === newId)) return` — sort sans rien faire en cas de collision, mais `NodeIdEditor`'s `draft` local garde le texte tapé (rejeté) affiché dans le champ, sans aucun message d'erreur. Donne l'impression que le renommage a marché (ou plante) alors qu'il a juste été ignoré.
**Fix** : petit — afficher une erreur inline (même pattern que les autres champs invalides) et/ou reverter visuellement `draft` à l'ancien id.

### 0.3 [x] Fait (2026-09-04, `51ca0da`) — aucune confirmation avant de perdre du travail non sauvegardé
Quitter l'éditeur (nouveau job jamais sauvegardé, ou modifications sur un job existant) via le bouton retour, le rail, ou en fermant l'appli ne prévient jamais — tout est perdu silencieusement. Aucun garde `beforeunload`/confirmation de navigation nulle part dans `AutomationPage`.
**Fix** : moyen — nécessite de suivre un état "dirty" (comparer le brouillon local à ce qui a été chargé/sauvegardé) puis un `window.confirm` ou une vraie modale avant de naviguer.

### 0.4 [x] Fait (2026-09-04, `c6ce91e`) — pas de suppression du job depuis l'éditeur lui-même
Seule l'Overview (la liste) permet de supprimer un job — il faut quitter l'éditeur pour ça, aucune option "Delete this automation" dans le canevas/topbar.
**Fix** : petit — ajouter l'action dans le drawer Job settings ou la topbar, réutilisant l'endpoint déjà utilisé par Overview.

### 0.5 [x] Fait (2026-09-04, `2f2a4fd`) — pas de reconnexion d'arête par glisser-déposer
Pour changer la cible d'une connexion existante, il faut la supprimer (sélection + Backspace, ou clic) puis en retracer une nouvelle depuis zéro — React Flow supporte le "reconnect" par glisser d'une extrémité d'arête existante (`reconnectable`/`onReconnect`) mais ce n'est pas branché dans `GraphEditor.tsx`.
**Fix** : petit — ajouter `onReconnect` (React Flow gère déjà la mécanique de drag, juste besoin du handler pour mettre à jour `edges`/appeler `emitChange`).

### 0.6 [x] Fait (2026-09-04, `551321a`) — pas d'annuler/refaire (undo/redo) sur le canevas
Aucun historique d'actions (ajout/suppression/déplacement de nœud, édition de paramètre) — une suppression accidentelle d'un nœud entièrement configuré est irrécupérable une fois qu'elle arrive (à part ne pas sauvegarder et recharger la page, perdant alors TOUT le reste du travail en cours). Ni React Flow ni le state React local (`useNodesState`/`useEdgesState`) ne gardent d'historique. Ce point n'était pas non plus ressorti dans l'audit n8n ci-dessus (nos agents de recherche ne l'ont pas creusé) — n8n a bien un vrai undo/redo (Ctrl+Z) au niveau du store du workflow, à vérifier plus précisément si ce chantier devient prioritaire.
**Fix** : moyen-gros — nécessite une vraie pile d'historique (snapshots de `nodes`/`edges`, ou un store type Zundo/temporal) plutôt qu'un correctif ponctuel.
**Filet de sécurité immédiat, sans construire tout un undo/redo** : au minimum, ajouter une confirmation avant `deleteSelectedNode()`/`onNodesDelete` (comme Overview le fait déjà pour supprimer un job entier) — n'empêche pas toutes les pertes accidentelles mais couvre le cas le plus fréquent (clic malheureux sur "Delete node").
**Fait, avec une portée délibérément limitée au canevas** : pile d'historique (past/future, 50 entrées max) poussée depuis `emitChange` — le seul point de passage commun à toute mutation (ajout/suppression/déplacement/duplication/renommage de nœud, connexion/reconnexion/suppression d'arête, sauvegarde de paramètres). Ctrl+Z / Ctrl+Shift+Z ou Ctrl+Y, plus deux boutons flottants en haut à gauche du canevas. L'undo au niveau du champ de texte lui-même (annuler une frappe dans le formulaire de paramètres) n'est pas couvert par ce chantier - déjà géré nativement par le navigateur pour un champ texte/textarea individuel tant qu'il a le focus, donc pas un vrai manque supplémentaire.

### 0.7 [x] Fait (2026-09-04, `5f83844`) — la touche "Suppr" (Delete) ne supprimait rien
Trouvé en testant en direct, pas dans la lecture de code initiale. `<ReactFlow>` n'avait aucun `deleteKeyCode` explicite — la valeur par défaut de la librairie est `'Backspace'` **seul**, qui n'inclut pas la touche Delete/Suppr (une touche physique distincte sur la plupart des claviers non-Mac). Corrigé avec `deleteKeyCode={['Backspace', 'Delete']}`.
