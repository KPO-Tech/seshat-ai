# SeshatOS — Comparaison avec OpenWork Den (plan de control plane entreprise)

*Étude comparative entre `seshat-server`/`seshat-console` et "OpenWork Den" (le control plane org de la plateforme OpenWork, `D:\Documents\PROJECTS\ai\helps\openwork\ee\`), pour identifier ce qui manque ou est mieux construit chez eux. Deux agents Explore dédiés (frontend `den-web`, backend `den-api`/`den-controller`/`den-gateway`/`den-worker-proxy`/`den-db`), suivis d'une vérification directe de l'état actuel de `seshat-server`/`seshat-console`.*

**Règle absolue, actée avec l'utilisateur avant de commencer : pas de copie littérale de code.** Le répertoire `ee/` d'OpenWork est sous la OpenWork EE License (source-available, pas MIT) — on peut lire, s'inspirer des patterns et de l'architecture, mais pas copier-coller ni redistribuer leur code. Chaque item ci-dessous est une fonctionnalité/pattern à reconstruire dans notre propre code, jamais un "porter tel quel".

## Résumé exécutif

- **Le trou le plus concret et le plus proche de ce qu'on vient de corriger** : `ProviderSetting` côté `seshat-server` n'a aucune notion de contrôle d'accès par membre/équipe à un provider IA — chez eux (`LlmProviderAccessTable`), un admin peut restreindre une clé API à des membres ou équipes précis, ou l'ouvrir à tous. Ça complète directement l'audit providers qu'on vient de faire côté SDK.
- **Le catalogue de providers dynamique (models.dev) est une meilleure architecture** que ce qu'on a (3 listes codées en dur qu'on vient de resynchroniser à la main). Pas un "manque" au sens strict, mais objectivement leur solution est plus robuste dans la durée.
- **SCIM est totalement absent** chez nous (front et back), alors qu'il est complet chez eux (SCIM 2.0, sync de groupes, retry/backoff, monitoring de santé).
- **SAML est absent** chez nous (on n'a que OIDC) — pas de vérification de propriété de domaine non plus.
- **Aucune politique desktop appliquée** — notre page `devices` ne fait que tracker, chez eux c'est un vrai système de gouvernance (catalogue déclaratif de policies + algorithme de fusion + restriction de version d'app).
- **Aucun diagnostic réseau self-service** pour l'IT d'entreprise — fonctionnalité simple, bien pensée, absente chez nous.
- **Point important pour notre propre licence** (`seshat-server/LICENSE`, brouillon calqué sur leur modèle) : chez eux, l'enforcement technique du seuil de 5 utilisateurs gratuits **n'existe que pour leur propre SaaS multi-org** (vérifié via Stripe). Pour un déploiement self-hosted comme le nôtre, **aucun enforcement technique n'existe** — uniquement contractuel. Leur code ne nous donne donc pas de modèle pour un enforcement technique côté self-hosted, si jamais on en veut un.
- **Bonne nouvelle** : `seshat-server` est déjà bien plus mature qu'on ne le pensait sur l'IAM de base (rôles custom, groupes, policy bindings, OIDC réel avec routes câblées et testées) — voir `audit-2026-08-13-enterprise-readiness.md` pour le détail (et noter que son affirmation "SSO inerte" est **périmée**, corrigée le 2026-08-15 selon `roadmap.md`).

### 3. SCIM (provisioning automatique depuis un IdP d'entreprise)

**Décision actée avec l'utilisateur (2026-08-29) : spec SCIM 2.0 complète (pas un increment minimal), découpée en étapes exécutables une par une, chaque étape devant être complète et vérifiée (build/test verts) avant de passer à la suivante — l'objectif est zéro retour en arrière architectural, pas la vitesse.**

Recherche préalable menée sur l'existant (`internal/server/db/models.go`, `internal/server/iam/{groups,invitations,members,oidc,provider_config,access,roles,audit}.go`, `internal/server/api/routes.go`, `internal/server/db/secrets.go`, `seshat-console/src/pages/providers/ProvidersPage.tsx`) pour ancrer chaque étape sur un pattern déjà éprouvé dans ce repo plutôt que d'improviser une architecture parallèle. Résumé des décisions de conception qui en découlent, avant le détail étape par étape :

- **`User.Email` est unique globalement et `Membership` impose un seul org par utilisateur** (`idx_membership_user`, `models.go`) — un utilisateur provisionné par SCIM ne peut donc appartenir qu'à l'organisation propriétaire de la connexion SCIM qui l'a créé. À vérifier/documenter explicitement dans le comportement d'erreur (409) si l'IdP tente de provisionner un email déjà membre d'une autre org.
- **Le provisioning SCIM doit suivre le chemin `CreateOrganizationMember` (`members.go`), pas `Invitation`** : création `User` + `Membership` (`status="active"` immédiatement, pas de pending/accept) dans la même transaction, mot de passe = hash d'un token aléatoire jamais révélé (l'utilisateur SCIM se connecte via le SSO de l'org, pas par mot de passe). `active:false` (création ou PATCH) → `Membership.Status="blocked"`, jamais une suppression de la ligne (pour que les PATCH ultérieurs par `externalId` continuent de matcher).
- **Le bearer token SCIM est un secret "à usage one-way"**, comme `Device.Token`/`Invitation.Token` : généré via `sdb.NewToken()`, stocké uniquement sous forme `sdb.HashOpaqueToken(raw)` (jamais déchiffré, jamais réaffiché après coup), comparé à la volée via `Where("token = ?", sdb.HashOpaqueToken(presented))`. Ne PAS utiliser `EncryptSecret`/`DecryptSecret` (réservé aux secrets qu'on doit relire, ex. clé API LLM) — mauvais outil pour ce cas.
- **Routing SCIM = pattern "Device protocol" (`routes.go` bas de fichier, `automation/devices.go`), pas pattern OIDC callback** : routes en `mux.HandleFunc` brut (jamais `app.authMiddleware`), un middleware dédié extrait le bearer via `bearerTokenFromRequest` (même helper que les sessions) puis résout une `ScimConnection` (pas un `iam.Principal`) par hash de token. L'organisation vient du token, pas de l'URL.
- **"File de retry avec backoff" (item hérité de la comparaison OpenWork) ne colle pas tel quel à un protocole SCIM, qui est push/synchrone (l'IdP appelle *notre* API et attend une réponse HTTP immédiate)** — corrigé dans le plan ci-dessous : la conformité aux codes d'erreur SCIM standard (400/409/500 bien formés) EST le mécanisme de retry, géré par le scheduler de l'IdP lui-même, pas par une queue interne à construire. Ce qui a un vrai sens à construire côté nous, c'est un **journal des tentatives récentes par connexion** (succès/échec, horodatage, ressource visée, message d'erreur) pour la visibilité admin (§ Étape 6) — pas une file de retry active.
- **Permissions** : nouvelle catégorie `scim_connections.read`/`scim_connections.manage` dans `permissionCatalog()` (`access.go`), à ajouter explicitement aux rôles `owner`/`admin` dans `roleCatalog()` (`roles.go`) — être dans le catalogue ne suffit pas, chaque rôle système liste ses permissions à la main.
- **Endpoints de découverte SCIM obligatoires en pratique** (`GET /ServiceProviderConfig`, `GET /ResourceTypes`, `GET /Schemas`) — la plupart des IdP réels (Okta, Entra ID, OneLogin) les interrogent à la configuration de la connexion et refusent de continuer s'ils sont absents, même s'ils ne servent plus après coup. Piège classique des implémentations SCIM maison à ne pas reproduire.

### 4. SAML + vérification de propriété de domaine

**Recherche préalable menée (2026-08-29)** sur l'infra OIDC/`Provider` existante avant de coder quoi que ce soit — résumé des trouvailles qui gouvernent le plan ci-dessous :
- `Provider.Kind` accepte déjà `"saml"`, la validation (`provider_config.go`) a déjà une vraie branche `"saml"` (pas un stub), et le formulaire `ProvidersPage.tsx` propose déjà `saml` dans le menu avec les 4 champs (`metadata_url`, `entity_id`, `sso_url`, `x509_certificate`) — **mais créer un provider SAML aujourd'hui ne fait strictement rien à la connexion** : `BeginOIDCLogin` rejette tout provider dont `Kind != "oidc"`, aucune route `/api/v1/auth/saml/*` n'existe. Piège UX silencieux pour un admin qui croirait avoir configuré du SSO.
- Aucune librairie SAML dans `go.mod` — `github.com/crewjam/saml` (référence Go, XML-DSig via `goxmldsig`) devra être ajoutée ; hors de question de vérifier une signature XML à la main.

- [x] **Fait (2026-08-29) — traité en premier, avant SAML, décision actée avec l'utilisateur.** Vérification de propriété de domaine par challenge DNS TXT. **Vraie faille trouvée en creusant, pas une amélioration de confort** : n'importe quel utilisateur authentifié pouvait déclarer `Organization.Domain = "gmail.com"` (ou le domaine d'une autre entreprise) sans aucune preuve — seule contrainte, qu'aucune autre org n'ait déjà pris exactement cette chaîne — et tout nouvel inscrit avec cet email s'auto-rejoignait ensuite en accès complet ("pending" = accès complet selon le code). #### Plan SAML détaillé en 5 étapes (écrit le 2026-08-29, même discipline que SCIM : chaque étape vérifiée build/test/live avant la suivante)

**Décisions de conception prises à partir de la recherche ci-dessus, avant de coder :**
- **SP-initiated uniquement** (pas IdP-initiated) — cohérent avec le flow OIDC existant (`BeginOIDCLogin` démarré par nous, jamais un callback non sollicité).
- **`Provider.EntityID`/`SSOURL`/`X509Certificate` décrivent l'IdP externe**, pas nous — même convention que `IssuerURL`/`ClientID` pour OIDC (le `Provider` décrit toujours le tiers, jamais ce serveur). Ce serveur a sa propre identité SP dérivée de `s.publicAPIURL` (comme `oidcRedirectURL`), mais **par provider, pas partagée** (correction faite pendant l'implémentation de l'Étape 2, voir plus bas pourquoi) : `EntityID`/métadonnées SP = `{publicAPIURL}/api/v1/auth/saml/{providerID}/metadata`, ACS URL = `{publicAPIURL}/api/v1/auth/saml/{providerID}/acs`.
- **Pas de clé de signature SP dans cette première version** : une `AuthnRequest` non signée en binding HTTP-Redirect est valide et acceptée par la quasi-totalité des IdP réels pour du SP-initiated — évite d'introduire une deuxième paire de clés (génération, stockage chiffré, rotation) avant d'avoir prouvé que le reste marche. Ajouter la signature SP restera possible plus tard sans tout casser (champ `Configuration` du modèle `Provider` peut porter ce besoin futur sans migration).
- **`x509_certificate` doit devenir obligatoire** pour un provider SAML (`provider_config.go` ne l'exige pas aujourd'hui) — sans lui, aucune vérification de signature d'assertion n'est possible, un trou de sécurité si on le laissait tel quel.
- **`github.com/crewjam/saml`** comme unique dépendance SAML — jamais de canonicalisation XML ni de vérification de signature à la main.
- Mapping identité : reproduire exactement l'arbre de décision d'`oidc.go` (auto-link si `AllowAutoLink` et email existant, provisioning si `AllowSignup` et email absent, rejet sinon), `NameID` (ou un attribut mappé via `ClaimMappings`) comme source de l'email, auto-join dans `Provider.OrganizationID` via l'équivalent de `oidcAutoJoinOrganization`.

### 5. Politiques desktop réellement appliquées

**Recherche préalable menée (2026-08-29)** sur l'infra existante avant de coder quoi que ce soit (deux agents Explore, un côté `seshat-server`, un côté `seshat-backend`/`seshat-ui`) — résumé des trouvailles qui gouvernent le plan ci-dessous :
- `Device` (`internal/server/db/models.go`) ne porte aujourd'hui strictement aucun champ de policy : `ID, OrganizationID, RegisteredByUserID, Name, Platform, AppVersion, Status, Token, LastSeenAt`. Zéro enforcement nulle part.
- `iam.PolicyBinding`/`CheckResourcePermission` (le mécanisme générique déjà réutilisé pour l'accès providers par membre/équipe) **ne convient pas tel quel** : il répond à "le sujet X a-t-il le code de permission P sur la ressource R ?", où P vient d'un catalogue de permissions CRUD fixe et R est une instance de ressource précise (un corpus, un provider setting) — pas une catégorie de fonctionnalité booléenne avec valeur par défaut et message utilisateur. `policies.read`/`policies.manage` (déjà dans `permissionCatalog()`) ne sont d'ailleurs que le garde-fou d'écriture du `PolicyBinding` existant lui-même, pas un concept de policy desktop. Ce qui **est** repris du pattern existant : la forme `SubjectType`/`SubjectID` (rôle/membre/groupe) et l'algorithme de correspondance de `bindingMatchesPrincipal` — mais dans une table neuve dédiée, pas en écrasant `PolicyBinding`.
- Auth "device protocol" déjà confirmée réutilisable (comme documenté pour SCIM) : `handleDeviceHeartbeat` extrait le bearer token brut côté handler HTTP et le passe tel quel à `Automation.Heartbeat(ctx, token)`, qui résout l'appareil lui-même — **exactement le point d'ancrage pour livrer un bundle de policies au device**, sans inventer un nouveau mécanisme d'auth.
- Côté desktop, chaque policy d'exemple a un point d'application net et différent :
  - **Providers personnalisés / modèles locaux** : un seul chokepoint, `seshat-backend/internal/settings/local_provider.go` (`LocalProvider.Create`) — aujourd'hui aucune validation contre un catalogue fixe, n'importe quel `provider`/`base_url`/`api_key` est accepté. Modèles locaux = Ollama aujourd'hui (pas de concept séparé), même chokepoint (`provider == "ollama"`).
  - **Plusieurs workspaces** : cible `seshat-backend`'s propre entité `Workspace` (`auth/service.go`, `CreateWorkspace`, déjà admin-only via `EnsureAdmin` mais sans plafond) — **à ne pas confondre** avec les "projects" 100% côté client (`localStorage`, `Sidebar.tsx`, aucune entité backend, donc impossible à policer côté serveur en l'état) ni avec la page `workspace/index.tsx` (constructeur d'agent, collision de nom sans rapport).
  - **Modification des réglages** : aucun garde-fou central aujourd'hui — 11 vues de réglages indépendantes côté `seshat-ui`, chacune avec ses propres appels API ; le seul point fiable est un **middleware backend** enveloppant les verbes d'écriture des groupes de routes "réglages" dans `seshat-backend`, pas une simple UI désactivée (qui n'empêcherait pas un appel API direct).
  - **Restriction de version d'app** : `Device.AppVersion` est stocké mais jamais comparé à quoi que ce soit — confirmé totalement absent, comme documenté dans l'audit dès le départ ("indépendant du système de policies de fonctionnalités").
- Livraison/cache côté desktop : le heartbeat (`seshat-backend/internal/cloud/automation`, toutes les 30s) est le point de greffe naturel pour recevoir un bundle de policies résolu — pas besoin d'un nouvel appel périodique. Le pattern de cache à imiter est `cloudidentity.Cache` (fenêtre de fraîcheur + fenêtre de grâce hors-ligne, persistée en DB locale), **pas** `cloudsettings.Provider` qui refait un aller-retour serveur à chaque appel sans tolérance hors-ligne.

**Décisions actées avec l'utilisateur (questions posées, 2026-08-29) :**
- **Résolution AND la plus restrictive** (pas OR comme OpenWork/comme `PolicyBinding` existant) : dès qu'**une seule** source applicable (défaut du catalogue, binding org-wide, binding de rôle, binding membre, binding équipe) dit `false`, l'effectif est `false` — même si une autre source dit `true`. Différent volontairement de l'algorithme OR pur de `bindingMatchesPrincipal`, ce n'est donc pas une extension de ce code existant mais un algorithme neuf.
- **Fail-open côté device non synchronisé** : un appareil qui n'a jamais reçu de bundle (premier lancement, hors ligne prolongé) traite tout comme autorisé par défaut — jamais bloqué avant d'avoir pu joindre le serveur au moins une fois. Distinct de la "valeur par défaut" du catalogue (qui s'applique côté serveur quand aucun binding ne cible l'org) : le fail-open est un comportement 100% côté client face à l'absence de toute donnée.
- **Spec complète tout de suite**, comme SCIM/SAML : le framework complet (catalogue, assignation, résolution, livraison) ET les 4 policies d'exemple ET la restriction de version d'app, étape par étape, chaque étape vérifiée build/test/live avant la suivante.

**Décisions de conception supplémentaires prises à partir de la recherche ci-dessus, avant de coder :**
- **Catalogue déclaré en code, pas en base** (comme `permissionCatalog()`) : les policies elles-mêmes (code, description admin, message utilisateur, valeur par défaut) sont un ensemble fixe que nous curons, pas quelque chose qu'un admin invente — seule leur **assignation** (par org/rôle/membre/équipe) vit en base.
- **Nouvelle table `DesktopPolicyBinding`**, pas de réutilisation de `PolicyBinding` (voir recherche ci-dessus) : `ID, OrganizationID, PolicyCode, SubjectType (org|role|user|group), SubjectID (vide pour org), Value bool, CreatedAt, UpdatedAt`, index unique sur `(organization_id, policy_code, subject_type, subject_id)` — un admin met à jour la valeur en place plutôt que d'empiler des bindings dupliqués pour le même sujet.
- **Nouveaux codes de permission** `desktop_policies.read`/`desktop_policies.manage` (pas de réutilisation de `policies.*`, qui gouverne déjà le `PolicyBinding` générique — les conflater masquerait deux concepts différents) — accordés à `owner`/`admin` comme tous les autres couples `.read`/`.manage`.
- **Toutes les policies par défaut préservent le comportement actuel (non restrictif)** : `allow_custom_providers`, `allow_local_models`, `allow_multiple_workspaces`, `allow_settings_modification` ont toutes `DefaultValue: true` — aucune installation existante ne se retrouve bridée du jour au lendemain ; un admin opte explicitement pour restreindre.
- **Résolution ciblée sur l'utilisateur qui a enregistré le device** (`Device.RegisteredByUserID` dans `Device.OrganizationID`) — un device "appartient" à la session connectée qui l'a enregistré, donc c'est ce principal dont les rôles/équipes comptent pour la résolution ; re-résolu à chaque heartbeat (~30s), donc convergent rapidement si la personne connectée change.

### 6. Diagnostic réseau self-service

**Recherche préalable menée (2026-08-29, un agent Explore dédié) avant de concevoir le plan** :
- `serverReachable` (`seshat-backend/internal/config/bootstrap.go:93-106`) est le seul diagnostic existant : un simple `GET /health` avec un timeout de 2s, sans détail par couche (DNS/TCP/TLS séparés) — une décision boot-time unique, pas un outil interrogeable à la demande.
- `/system/status` (`seshat-backend/internal/api/system.go`) est un instantané de configuration statique (`mode`, `server_url`, sandbox, docling, local STT, image generation) — pas une sonde réseau live.
- Aucun bouton "tester la connexion" n'existe nulle part (ni providers LLM, ni MCP, ni OIDC/SAML, ni SCIM) — confirme l'item 1 encore ouvert sur ce point précis (`docs/helps/audit-2026-08-29-openwork-den-comparison.md` § 1, "Bouton tester la connexion").
- `defaultServerURL` (`bootstrap.go:77-85`) est une constante fixée au build (`http://localhost:8081` aujourd'hui, une vraie URL de prod une fois `seshat-server` déployé), délibérément non configurable — donc une cible fixe et unique du point de vue diagnostic, exactement le modèle "client desktop d'entreprise qui parle à une seule API centrale" que décrit OpenWork.
- Côté `seshat-server`, deux dépendances sortantes réelles pour l'IT d'entreprise : le relais SMTP (`mailer.Config`, `SESHAT_SERVER_SMTP_*`) pour les emails d'invitation/reset, et les endpoints IdP configurés par org (`Provider.IssuerURL` pour OIDC — c'est le seul champ réellement utilisé à l'exécution, `oidc.go:154` ; `Provider.SSOURL` pour SAML — `MetadataURL`/`DiscoveryURL` existent en base mais ne sont **jamais** exploités dynamiquement par le code actuel, voir `saml.go:415-417` : cibler ces champs non-utilisés serait trompeur).

**Décision actée avec l'utilisateur (question posée, 2026-08-29) : périmètre "Desktop + Serveur"** — un diagnostic côté `seshat-ui`/`seshat-backend` (ce poste → l'API centrale Seshat) ET un diagnostic côté `seshat-console`/`seshat-server` (le serveur → ses propres dépendances sortantes SMTP/IdP), plutôt que le scope plus étroit "desktop uniquement" qui collait le plus littéralement à la description de l'audit.

**Décisions de conception prises à partir de la recherche ci-dessus :**
- **Primitif de sondage en couches** (DNS → TCP → TLS si `https` → HTTP), dupliqué à la main dans les deux dépôts Go (`seshat-backend`, `seshat-server`) — pas de package partagé possible entre deux modules Go séparés (même contrainte déjà rencontrée avec les codes `DesktopPolicyAllow*`). Chaque étape reporte succès/échec, durée, un détail (IPs résolues, code HTTP) et — seulement en cas d'échec — une suggestion ciblée avec un "à qui la faute" (`network_admin`, `it_security`, `support`).
- **Le succès de l'étape HTTP = pas d'erreur de transport, jamais un code de statut précis** — pertinent pour `/health` (qu'on contrôle, où 200 a un sens), mais surtout indispensable pour les endpoints tiers (IdP, SMTP) où un 404/405 sur un GET nu ne prouve rien de cassé côté réseau ; le code de statut réel reste visible dans le détail, pour information seulement.
- **SMTP n'a pas d'étape TLS** : le port 587 (STARTTLS) négocie le TLS *après* la connexion en clair — un `tls.Dial` immédiat y échouerait systématiquement pour un relais parfaitement fonctionnel. Seuls DNS+TCP sont vérifiés pour SMTP (suffisant pour la question "un pare-feu bloque-t-il ce port").
- **Nouveau code de permission `network_diagnostics.read`** (pas de réutilisation de `providers.read`) — deux capacités différentes : voir la config d'un provider n'est pas la même chose que déclencher une sonde réseau active vers son endpoint. Accordé à `owner`/`admin`.
- **`mailer.SMTPSender` gagne une interface optionnelle `SMTPTarget() (host string, port int, ok bool)`**, pas une extension de `Sender` lui-même (qui n'a besoin que de `Send` pour tout le reste, y compris les doublures de test) — `iam.Service` fait un type-assert best-effort dessus.

**Recherche préalable menée (2026-08-30, trois passes) avant de concevoir le plan** :
- Les 3 sous-points de l'item n'ont rien en commun en taille : `skillregistry`/`agentregistry`/`mcpregistry` sont trois packages Go structurellement parallèles mais totalement indépendants (pas de table partagée, seul lien faible : `AgentPreset.McpServers []string`, une liste de noms non contrainte par une FK). Aucune des trois n'a de notion "installé vs. catalogue disponible" — tout ce que l'org possède est automatiquement actif à la résolution (`mcpregistry.ResolveServerConfigs`, `skillregistry` via le filesystem, `agentregistry.ListPresets`).
- **"Commandes" n'est pas un concept distinct** : les commandes slash de `seshat-ui` (`ChatInput.tsx`) sont directement alimentées par `/skills` (`seshat-backend/internal/skills`) — un "bundle" n'a donc que 4 composants réels (skills, MCP, agent presets, hooks), pas 5.
- **"Hooks" existe déjà comme mécanisme moteur dans le SDK `seshat`, mais nulle part comme concept produit.** `internal/hooks/hook.go` (SDK) implémente un vrai système PreToolUse (matcher regex, décisions allow/deny/halt/rewrite-input/inject-context, format calqué sur Claude Code/crush) et `pkg/sdk/client_config.go` l'expose (`ClientConfig.PreToolHooks []PreToolHookConfig{Matcher, Command, Timeout}`). **Mais `EnableHooks`/`PreToolHooks` ne sont jamais peuplés nulle part côté produit** : `seshat-server/internal/server/workspacechat/service.go` et `seshat-backend/internal/workflows/service.go` mettent `EnableHooks: false` explicitement ; `seshat-backend/internal/config/bootstrap.go:808` (le vrai moteur de chat interactif, `internal/query`, distinct de `internal/workflows` qui n'est que le runner du designer de workflows) omet carrément les deux champs. Aucune table DB, aucune API admin, aucune UI console pour les hooks — c'est un chantier entièrement neuf côté produit, même si le moteur bas niveau existe.
- **Trouvaille de sécurité qui a tranché le périmètre des hooks** : `internal/hooks/hook.go:190` (SDK) exécute chaque hook via `exec.CommandContext(shell, "-c", cfg.Command)` **sans passer par le sandbox Docker/Landlock** déjà utilisé pour l'outil bash — un simple `os/exec` brut. `workspacechat` (le chat exécuté **à l'intérieur de `seshat-server`**, le process partagé par toutes les organisations d'un déploiement) ne peut donc PAS activer des hooks admin-configurables sans permettre à une seule organisation de compromettre le serveur de toutes les autres — ce n'est pas un arbitrage de risque comparable à la garde SSRF de l'item 8 (où l'admin a déjà une capacité équivalente), c'est une brèche d'isolation multi-tenant concrète, et la corriger demanderait de modifier le SDK tiers lui-même (hors de ce monorepo).
- **Aucun mécanisme d'export/import n'existe nulle part** dans le produit (aucune fonction `Export`/`Import`, aucun format de manifeste JSON/YAML en usage) — et aucune infrastructure d'hébergement/découverte de bundles entre organisations (pas de CDN, pas de registre public, pas de modération).
- Livraison des configs MCP côté `seshat-backend` (le pattern à imiter pour les hooks) : un **pull authentifié**, pas un push par heartbeat — `internal/mcp/service.go` résout le catalogue org (`ListOrgCatalog`), croise avec des **approbations locales explicites** (`db.MCPOrgServerApprovalStore` — un serveur MCP poussé par l'org ne s'active jamais sans que l'utilisateur du device l'approuve lui-même), puis `Reload` appelle `SDKRuntime.ReloadMCPServers` — un vrai hot-reload sans redémarrage. **Lacune SDK découverte en creusant** : il n'existe pas de `ReloadPreToolHooks` équivalent pour les hooks (contrairement à `ReloadMCPServers`) — contournable côté `seshat-backend` sans toucher au SDK en enregistrant un seul `ToolHook` durable via `AddToolHook` dont la fonction `Execute` lit un runner remplaçable protégé par mutex, plutôt que ré-enregistrer un hook à chaque rechargement.

**Décisions actées avec l'utilisateur (questions posées, 2026-08-30) :**
- **Hooks limités au desktop (`seshat-backend`) pour l'instant** — jamais dans `workspacechat`/`seshat-server`, pour la raison de sécurité ci-dessus. Le support `workspacechat` reste documenté comme bloqué sur un changement en amont du SDK (sandboxing de l'exécution des hooks), pas abandonné mais pas fait tant que cette base n'existe pas. **Correction opérée en cours de recherche** : la question initiale proposait "desktop + serveur partagé" et l'utilisateur avait d'abord choisi cette option plus large ; la trouvaille du `exec.CommandContext` non sandboxé (un fait de code, pas une supposition) a changé la donne et l'utilisateur est revenu sur "desktop uniquement" une fois le risque concret montré.
- **Bundle = export/import de manifeste, pas un marketplace hébergé** — un bundle est un fichier JSON portable qu'un admin exporte depuis son org et qu'un autre admin (ou lui-même, plus tard) réimporte ; pas de service d'hébergement/catalogue à construire, cohérent avec l'infrastructure réellement disponible.
- **Périmètre complet malgré la taille** (décision explicite, l'utilisateur a choisi cette option en connaissance de cause du coût) : inventer les hooks de zéro plutôt que de se limiter à un bundle sans hooks, parce que c'est objectivement le sous-chantier le plus efficace des trois pour l'expérience "marketplace" (une capacité complète en une action plutôt que N formulaires séparés), même si c'est le plus coûteux à construire.

**Décisions de conception supplémentaires :**
- **Nouveau package `internal/server/hookregistry`** (`seshat-server`), miroir structurel de `mcpregistry`/`skillregistry` : table `HookConfig` org-scopée (`Matcher`, `Command`, `Timeout`, `Name`, `Enabled`), permissions `hooks_registry.read`/`.manage` (owner/admin), CRUD + endpoint de résolution `GET /api/v1/hook-configs/resolve`.
- **Nouveau package `internal/hooks` côté `seshat-backend`**, miroir du pattern MCP (`internal/mcp/service.go`) : résolution du catalogue org + **approbation locale explicite obligatoire** (nouvelle table, même esprit que `MCPOrgServerApprovalStore`) — un hook poussé par l'org ne s'exécute jamais sans que l'utilisateur du device l'ait approuvé lui-même. C'est encore plus important que pour MCP : un hook s'exécute automatiquement à *chaque* appel d'outil, silencieusement, alors qu'un serveur MCP stdio est une action ponctuelle et visible.
- **Câblé aux deux moteurs de `seshat-backend`** qui construisent leur propre `sdk.ClientConfig` indépendamment (pas un point de câblage unique) : `internal/config/bootstrap.go` (`queryClientConfig`, le chat interactif réel) et `internal/workflows/service.go` (le runner du designer de workflows).
- **Nouvelle table de traçabilité `BundleImport`** (pas une colonne ajoutée aux 4 tables existantes) : `ID, OrganizationID, BundleName, ImportedByUserID, ImportedAt`, plus une table de jonction `BundleImportItem{BundleImportID, ResourceType, ResourceID}` — permet d'afficher "vient du bundle X" sur chaque item créé par un import ET de retirer un bundle entier plus tard sans toucher au schéma des 4 tables de registre existantes.
- **Le 3ᵉ sous-point de l'item (modèle de provenance) est refermé par construction** en même temps que le bundle : `BundleImportItem` donne "vient du bundle X" ; `CreatedByUserID` (déjà stocké mais jamais affiché sur aucune des 4 pages) donne "créé par moi" ; le `Source: "organization"|"platform"` déjà existant sur skill repos/MCP donne "catalogue plateforme" — les trois signaux existent déjà après le chantier bundle, il ne reste qu'à les afficher.

### 8. UX de connexion MCP ("Smart-Add")

**Recherche préalable menée (2026-08-29, deux passes) avant de concevoir le plan** :
- 4 `server_type` existent (`stdio`, `http`, `sse`, `websocket` — `MCPServersPage.tsx`, `SERVER_TYPE_OPTIONS`), aucune validation stricte côté Go (`mcpregistry.CreateServerConfig` défaut sur `stdio` si vide, sinon accepte n'importe quelle chaîne en minuscules). `stdio` exécute une commande locale sur le device connecté — hors de portée d'un "Smart-Add par URL", qui ne peut concerner que `http`/`sse`/`websocket`.
- **Aucune infra OAuth MCP réutilisable n'existe nulle part**, ni dans `seshat-server` ni dans le SDK `seshat` vendored (`internal/tools/system/mcp/config.go:481-513`) : `MCPOAuthConfig`/`ShouldUseOAuth`/`ConnectWithOAuth` sont un stub non fonctionnel — deux variables d'env globales (`SESHAT_MCP_CLIENT_ID`/`AUTH_URL`), aucun échange de code réel, `ConnectWithOAuth` logue puis retombe sur `Connect` sans rien faire d'autre. Zéro découverte `WWW-Authenticate`/`.well-known/oauth-*` nulle part dans le SDK ou le serveur (vérifié par recherche exhaustive). Un vrai flow OAuth pour un serveur MCP tiers **inconnu** nécessiterait du Dynamic Client Registration (RFC 7591) — on n'a pas de client OAuth pré-enregistré comme pour Google Drive/SharePoint (qui, eux, utilisent un vrai pattern popup+polling réutilisable : `connectors/oauth.go`, `BeginConnectorOAuth`/`CompleteConnectorOAuth`, état à usage unique + PKCE, et côté frontend `window.open(authorization_url)` + une liste qui repolle toutes les 5s pour "récupérer" le résultat du callback sans écouteur de fenêtre dédié — `ConnectorsPage.tsx:552-568`, `useMyConnectorAccountsList`).
- `Headers`/`Env` sont déjà un magasin clé/valeur chiffré générique et symétrique (`encryptSecretMap`, `mcpregistry/service.go:479-500`) — une étape "coller une clé API" peut réutiliser ce mécanisme tel quel (`Headers["Authorization"] = "Bearer <clé>"`), zéro changement backend nécessaire pour ce cas.
- Aucun bouton "tester la connexion" n'existe aujourd'hui pour un serveur MCP (`MCPServerFormDrawer` va droit à la mutation `create`/`update`, aucune validation asynchrone).

**Décision actée avec l'utilisateur (question posée, 2026-08-29) : détection + credential manuel, pas d'OAuth automatisé.** Un vrai flow OAuth complet (découverte + Dynamic Client Registration + popup/polling + stockage/refresh de tokens par connexion MCP) serait un chantier à l'échelle de SAML/SCIM pour un item que l'audit qualifie lui-même de "pas urgent, gain UX". Le choix retenu : sonder l'URL sans authentification ; une réponse `2xx` crée l'entrée immédiatement (le vrai gain UX : un seul champ au lieu du formulaire complet) ; une réponse `401`/`403` demande un seul champ credential (jeton/clé déjà obtenu par l'admin, jamais un échange OAuth automatisé) puis re-sonde avec ce credential avant de créer, pour ne jamais enregistrer une entrée dont on sait déjà qu'elle ne fonctionnera pas.

**Décisions de conception supplémentaires :**
- La sonde envoie une vraie requête JSON-RPC 2.0 `initialize` (le handshake MCP réel, pas un GET nu qui se ferait rejeter à tort par un serveur exigeant `POST`) et classe la réponse : `2xx` → `none` (type deviné via `Content-Type` : `text/event-stream` → `sse`, sinon `http`) ; `401`/`403` → `credential` (détail = `WWW-Authenticate` si présent, sinon le code brut — jamais de tentative de parser une métadonnée OAuth, on ne l'utilise pas) ; tout le reste (4xx/5xx ambigus, ou erreur de transport) → `unknown`, avec le détail brut, laissé à l'appréciation de l'admin plutôt que de deviner silencieusement "aucune auth requise" et risquer de créer une entrée cassée sans le dire.
- `ws`/`wss` explicitement hors de portée de la sonde (une prise WebSocket ne se sonde pas avec une requête HTTP) — Smart-Add retombe sur "essaie quand même" ou le lien "Configuration manuelle", limitation assumée et documentée, pas un bug.
- **Pas de garde SSRF ajoutée sur l'URL sondée**, décision délibérée : cette action est gardée par `mcp_registry.manage`, la même permission qui autorise déjà de configurer un serveur `stdio` — c'est-à-dire l'exécution de commandes arbitraires sur un device connecté. Bloquer les IPs privées/loopback pour une simple requête HTTP en lecture sous ce même niveau de confiance serait du théâtre de sécurité, pas une vraie protection, et casserait des cas d'usage légitimes (serveur MCP interne à l'entreprise, test en local).
- Smart-Add devient le point d'entrée **par défaut** du bouton "New MCP server", avec un lien "Configuration manuelle" qui bascule vers le formulaire complet existant (`MCPServerFormDrawer`, inchangé) — couvre `stdio`, `websocket`, et tout cas où la détection se trompe.

### 9. Ré-authentification "step-up" avant une action sensible

**Recherche préalable menée (2026-08-30) avant de concevoir le plan :**
- **Aucun pattern step-up réutilisable n'existe.** Le seul analogue est `ChangePassword` (`iam/password.go`) — un champ `current_password` revérifié en bcrypt, mais câblé en dur pour ce seul endpoint, pas un mécanisme partagé.
- **Un re-check par mot de passe seul ne peut pas fonctionner pour les comptes SSO.** Les utilisateurs provisionnés via OIDC/SAML/SCIM reçoivent un `PasswordHash` aléatoire et inconnu par construction (`oidc.go:239`, `scim_provisioning.go:46`) — pas de mot de passe à resaisir. **Décision actée avec l'utilisateur** : construire les deux chemins (mot de passe ET OIDC/SAML), pas seulement le premier, malgré le fait que côté `seshat-console` (seul endroit où vivent les 4 actions ciblées), **aucune session n'est jamais authentifiée via SSO aujourd'hui** (`grep` exhaustif de `src/pages/auth/` et de toute référence à `/auth/oidc/`/`/auth/saml/` côté console : aucun résultat) — le login console est mot de passe/invitation/bootstrap uniquement. Le chemin OIDC/SAML sera donc backend-complet et testé (faux IdP, même pattern que `oidc_test.go`/`saml_test.go`) mais sans déclencheur UI tant que le login SSO n'existe pas côté console — assumé explicitement, pas un oubli.
- **"Transférer la propriété d'une org" n'existe pas comme fonctionnalité** ici — "owner" est juste un code de rôle (`iam/roles.go`), pas un concept de transfert. Les 4 actions réellement destructrices/à fort impact identifiées dans le code, sans aucune confirmation au-delà du contrôle de permission normal : `iam.Service.DeleteOrganization`, `iam.Service.DeleteUser`, `iam.Service.DeleteProvider` (supprime un provider IA **ou** un provider SSO OIDC/SAML actif — verrouille potentiellement toute l'org hors SSO), `scim.Service.RotateConnectionToken` (invalide immédiatement le jeton que l'IdP utilise). **Décision actée avec l'utilisateur** : les 4 sont dans le périmètre.
- **`Session` (`db/models.go:143`) n'a aujourd'hui aucune notion de fraîcheur d'authentification** — juste `Token`/`ID`/`UserID`/`CreatedAt`/`ExpiresAt`. `Principal.Session` (domaine, `iam/service.go:93`) est déjà résolu une fois par requête (`ResolvePrincipal`) et porté sans requête supplémentaire jusqu'aux points d'appel — c'est l'ancrage naturel pour porter un champ de fraîcheur sans requête DB additionnelle à chaque contrôle.
- **Le callback OIDC/l'ACS SAML sont des routes fixes par provider, indépendantes du fait qu'on est en train de se connecter ou de faire un step-up** (`s.oidcRedirectURL(providerID)`/`s.samlACSURL(providerID)`, jamais paramétrées par l'appelant) — donc réutiliser exactement la même route pour le step-up ne demande **aucune reconfiguration côté IdP** (le `redirect_uri`/l'URL ACS enregistrée chez le client reste identique). C'est la contrainte qui a guidé la conception ci-dessous : un état de step-up séparé, mais la même route de callback, désambiguïsée par une table d'état différente.

**Conception :**

1. **Fraîcheur de session** : `sdb.Session.ReauthenticatedAt time.Time` (non nullable, jamais zéro) — initialisé à `now` dans `newSession` (point de construction unique partagé par login mot de passe/OIDC/SAML/superadmin), donc une connexion fraîche compte déjà comme une preuve d'identité récente (pas de step-up exigé juste après un login — même logique que le "sudo mode" de GitHub). Mis à jour à `now` par un step-up réussi. `iam.Service.RequireFreshAuth(principal) error` compare `time.Since(principal.Session.ReauthenticatedAt)` à `stepUpFreshnessTTL` (15 min) — pas de requête DB supplémentaire, la session est déjà chargée dans `Principal`.
2. **Code d'erreur dédié** : `apperr.StepUpRequired(message)` (nouveau `Kind: "step_up_required"`), mappé en HTTP **428 Precondition Required** (RFC 6585, distinct de 401/403) avec un champ `code` ajouté au corps JSON **uniquement pour ce Kind** (`{"error":{"message":"...","code":"step_up_required"}}`) — tous les autres messages d'erreur gardent exactement leur forme actuelle, aucune régression de contrat pour les consommateurs existants qui ne lisent que `.error.message`.
3. **Step-up mot de passe** : `POST /api/v1/auth/step-up/password { current_password }` (authentifié) — revérifie en bcrypt (même logique que `ChangePassword`), mutation directe de `Session.ReauthenticatedAt`.
4. **Step-up OIDC/SAML — sans toucher au comportement de connexion existant** : nouvelles tables `OIDCStepUpState`/`SAMLStepUpState` (miroir de `OIDCLoginState`/`SAMLAuthRequestState`, plus `SessionID`+`UserID` — quelle session existante élever, jamais une nouvelle). `BeginOIDCStepUp`/`BeginSAMLStepUp` : authentifiés, et `redirect_uri` validé contre `s.publicAppURL` (l'origine unique et déjà configurée du frontend web — **pas** `requireLoopbackRedirectURI`, qui suppose un client natif comme le desktop ; c'est une vraie divergence délibérée, pas un oubli). `CompleteOIDCLogin`/`CompleteSAMLLogin` gagnent une **pré-vérification bon marché en tête de fonction** (recherche dans la table de step-up avant tout le reste) qui délègue à un nouveau chemin `completeOIDCStepUp`/`trySAMLStepUp` séparé si l'état correspond à un step-up — **le corps existant de la connexion normale reste intact, zéro branche ajoutée dedans**, pour que rien ne puisse faire dévier accidentellement le chemin de login (déjà durci, déjà testé) vers une création/liaison de compte pendant un step-up. Le chemin step-up n'appelle jamais le code de provisioning : un email résolu qui ne correspond pas exactement au `UserID` stocké dans l'état est un rejet, jamais une auto-liaison. Extraction d'un petit helper partagé `oidcVerifyCallback` (échange de code + vérification ID token + nonce + email_verified) réutilisé par les deux chemins OIDC, pour ne jamais dupliquer une vérification de sécurité en deux endroits qui pourraient dériver l'un de l'autre.
5. **Câblage** : `RequireFreshAuth(principal)` ajouté juste après le contrôle de permission existant dans `DeleteOrganization`/`DeleteUser`/`DeleteProvider`/`RotateConnectionToken`.
6. **Frontend `seshat-console`** : interception générique dans `src/api/client.ts` sur `code: "step_up_required"` → modale "Confirmez votre identité" (mot de passe uniquement, seul chemin atteignable aujourd'hui) → rejoue automatiquement la requête d'origine après un step-up réussi. Un seul point d'interception générique, aucune des 4 mutations concernées n'a besoin d'être modifiée individuellement.

### 9bis. Login SSO pour `seshat-console` (referme le "code mort" du step-up OIDC/SAML de l'item 9)

**Motivation (2026-08-30, demande explicite de l'utilisateur)** : l'item 9 a livré un step-up OIDC/SAML backend-complet et testé, mais sans déclencheur UI possible puisque `seshat-console` n'a jamais eu de login SSO du tout — fonctionnellement correct, mais du code mort en pratique côté produit. Fermer ce gap rend le step-up OIDC/SAML réellement atteignable.

**Recherche préalable** :
- `LoginPage.tsx` est aujourd'hui un simple formulaire email+mot de passe global, sans aucune notion d'organisation ni de provider avant l'authentification.
- `BeginOIDCLogin`/`BeginSAMLLogin` exigent `requireLoopbackRedirectURI` (pattern app native, RFC 8252) — un `redirect_uri` web (`https://console...`) est aujourd'hui rejeté par construction, jamais testé pour ce cas.
- `Provider.AllowedDomains` existe déjà en base (utilisé jusqu'ici uniquement pour l'auto-join **après** authentification) — donnée directement réutilisable pour la découverte **avant** authentification.
- **Décision actée avec l'utilisateur** : découverte "email d'abord" (l'utilisateur saisit son email, le serveur regarde si un domaine correspond à un provider actif, propose "Continuer avec {IdP}" si oui, sinon révèle le mot de passe normalement) plutôt qu'un slug d'organisation dans l'URL — réutilise une donnée déjà en base, ne demande rien de nouveau à l'utilisateur, même pattern que Slack/Okta/Notion.

**Conception :**
1. **`iam.Service.LookupSSOProviderForEmail(ctx, email)`** : charge tous les `Provider` `Kind IN (oidc, saml)` `Enabled=true` (table de petite taille par déploiement — un scan complet plutôt qu'une requête JSON fragile sur la colonne sérialisée `AllowedDomains`) et filtre en Go sur une correspondance de domaine insensible à la casse. Retourne `nil, nil` (jamais une erreur) en l'absence de correspondance — c'est une découverte, pas une validation. Départage déterministe mais non résolu si deux organisations distinctes revendiquent le même domaine (limitation documentée, acceptable : le cas d'usage principal de ce produit est le self-hosted mono-org).
2. **`POST /api/v1/auth/sso-lookup { email }`** (public, même limiteur de débit que `/auth/login`).
3. **`requireLoopbackOrConsoleRedirectURI`** : nouvelle validation utilisée par `BeginOIDCLogin`/`BeginSAMLLogin` à la place de `requireLoopbackRedirectURI` seul — accepte le loopback (app desktop, comportement inchangé) **ou** l'origine `publicAppURL` déjà configurée (réutilise `requireConsoleRedirectURI`, posé pour le step-up). Purement additif : tout `redirect_uri` déjà accepté avant continue de l'être.
4. **Frontend** : `LoginPage.tsx` en deux temps (email → "Continuer" → si un provider correspond, bouton "Continuer avec {IdP}" + lien "utiliser un mot de passe à la place" ; sinon le champ mot de passe apparaît directement, comportement inchangé). Nouvelle page `SSOCallbackPage.tsx` (`/auth/sso-callback`, publique) qui lit `?token=` et le persiste via un nouveau `useAuthStore.setToken` (laisse `user`/`organizations`/`memberships` à `null` — l'hydratation `/auth/me` déjà existante de `ProtectedRoute` s'en charge, exactement comme un rafraîchissement de page le fait déjà).

**Plan d'exécution :**

## 💡 Patterns d'architecture à adopter (indépendants de toute fonctionnalité précise)

- [x] **Recherché (2026-08-30) — reporté, décision actée avec l'utilisateur.** `OrganizationOverviewPage.tsx` fait bien 11 appels séparés au chargement (organisations, memberships, invitations, jobs, devices, corpora, runs, audit events, provider settings, embedder, applications — ~6 services backend distincts). Mais ces 11 appels partent déjà en parallèle via React Query (pas une cascade séquentielle), et HTTP/2 les multiplexe sur une seule connexion — le vrai gain d'un endpoint agrégé serait de remplacer "N allers-retours simultanés" par "1 aller-retour dont le serveur fait le travail en interne", ce qui ne vaut vraiment le coup que si la latence réseau elle-même est le goulot (connexion distante/mobile), pas le nombre de requêtes en soi — peu probable pour une console d'admin interne. Coût concret et immédiat en face : un nouvel endpoint orchestrant ~6 services backend différents, à maintenir en plus des 11 endpoints existants (toujours utilisés individuellement ailleurs dans la console). Reporté, pas abandonné.
- [x] **Fait (2026-08-30).** Étendre l'usage du flag `org_mode`. Recherché d'abord (agent Explore) : côté serveur, `org_mode` ne gate qu'un seul point (`CreateOrganization` refuse une deuxième org en mode `single`) ; côté console, seuls deux boutons "create organization" en tenaient compte — tout le reste de la navigation suppose le multi-org sans condition. Trouvé concrètement confus pour un opérateur mono-org : l'entrée de nav "Organizations" (liste/CRUD d'organisations, avec des contrôles "organisation par défaut de la plateforme" et "partagé avec toutes les organisations" qui n'ont aucun sens s'il ne peut y avoir qu'une seule org), la page `/my-organizations` ("Organizations you're a member of"), et le bouton "Back to Organizations" du sidebar admin. Nouveau `useOrgMode()` (`api/auth.ts`, lit `bootstrap-status` déjà chargé, `undefined` traité comme multi tant que non résolu — dégrade vers le comportement actuel plutôt que de cacher de la navigation par erreur). `AppLayout.tsx` retire l'entrée "Organizations" du groupe Platform et repointe "Back to Organizations" vers `/platform/overview` (rebaptisé "Back to Platform") en mode single. Nouveau garde `RedirectIfOrgModeSingle` (défense en profondeur, miroir de `RequireSuperAdmin`) enveloppant `/platform/organizations` et `/my-organizations` — redirige vers la route d'atterrissage normale de l'utilisateur (pas une destination fixe, puisque ce garde protège à la fois une route superadmin-only et une route membre normal) en cas d'accès direct par URL/marque-page/retour navigateur. `tsc -b`, `oxlint src`, `npm run build` (production) verts — aucun changement backend nécessaire (`org_mode` et son enforcement existaient déjà côté serveur).
- [x] **Recherché (2026-08-30) — décliné pour l'instant, pas un refactor de nettoyage.** Un agent Explore a vérifié l'état réel : aucun hook `usePermission`/`hasPermission` partagé n'existe, et un seul vrai site d'appel fait un check de permission par code (`RequireOrganizationManager.tsx:20-21`, `membership.permissions?.includes('organization.manage')`) — `RequireSuperAdmin.tsx` utilise un mécanisme différent (`user.is_admin`, un flag plateforme, pas un code de permission). **Aucune des ~30 pages sous `/orgs/:organizationId/*` ne fait de check de permission fin par action** (créer/éditer/supprimer) — elles sont toutes derrière la même porte unique tout-ou-rien (`organization.manage`), donc il n'y a pas de duplication à corriger aujourd'hui. La valeur d'une centralisation serait uniquement préventive (éviter que ces ~30 pages n'accumulent chacune leur propre `membership.permissions.includes(...)` codé en dur le jour où des permissions plus fines sont ajoutées), pas un nettoyage d'un problème existant — construire ça maintenant serait de l'infrastructure pour un besoin hypothétique, contraire à la discipline du projet. Reporté sans être abandonné : à reconsidérer le jour où une première page a réellement besoin d'un check plus fin que la porte de route actuelle.

## ⚖️ Note sur l'enforcement de licence (pas un item d'action — contexte pour une décision produit)

Chez OpenWork, le seuil "gratuit jusqu'à 5 utilisateurs" n'est technique­ment appliqué **que pour leur propre offre SaaS multi-org**, via une vérification Stripe au moment de créer une invitation. **Pour un déploiement self-hosted (single-org) — notre cas — il n'existe aucun enforcement technique chez eux non plus**, uniquement le texte de licence.

Si on veut un jour un enforcement technique réel pour les self-hosters de `seshat-server`, leur code ne fournit pas de modèle pour ça — c'est une question produit/business à trancher séparément (clé de licence validée côté serveur ? build entreprise distinct ? rien du tout, comme eux ?), pas une sous-tâche technique à déduire de leur exemple.
