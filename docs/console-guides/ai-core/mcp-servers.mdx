# MCP Servers

`/orgs/:id/mcp-servers` — Organization → AI Core → MCP Servers

## What it's for

Defining, once, which MCP (Model Context Protocol) tool servers this
organization's agents are *allowed* to use — Jira, GitHub, a self-hosted
internal tool, anything speaking the MCP protocol. This page is the
catalog definition only. It does not run anything, and it is not where a
person decides whether *they* want to use one — see "Two separate
decisions" below, easy to conflate and worth reading if MCP behavior
looks incomplete.

## How to use it

"New MCP server" opens Smart-Add by default: paste a URL, it probes the
server with a real handshake and tells you whether it needs a credential
before you fill out anything else. Stdio and websocket servers, or
anything the probe can't classify, fall back to the full manual form
(name, type, command/args for stdio, url/headers for remote, timeout,
icon).

"Bridged account" (`connector_kind`) is the field that matters most for
vendor tools: when set, each employee's *own* connected account
(Workspace → Connections) gets bridged in as that server's Authorization
header automatically — the agent acts as that specific person, not a
shared organization identity. Picking a known kind (Slack, Notion,
GitHub, Stripe, ...) pre-fills the vendor's official MCP endpoint too.

## Two separate decisions

Defining a server here (admin, this page) and actually running it
(each employee, on their own device) are deliberately two different
decisions, made in two different places:

- **This page** answers "is this server part of the organization's
  catalog at all." Admin-only, org-wide.
- **seshat-ui's Workspace → Tools & MCP → "Organization catalog"**
  answers "do *I* want to run this locally." Every employee approves
  (or revokes) each catalog entry individually, for their own device —
  this applies to every server type, not just stdio ones that spawn a
  local process; a remote HTTP/SSE server still needs the same explicit
  approval before an employee's device will call it.

A server defined here with nobody having approved it yet is inert —
listed, but not actually usable by anyone until at least one employee
turns it on for themselves.

## Which vendors actually work, and how

Not every vendor with a connector account has a matching MCP *tool* —
having one lets an agent call the vendor's API as a tool mid-conversation;
not having one just means that vendor's data can still be used other
ways (Knowledge sync, dataflow automation nodes), just not as a live
agent tool call. Three groups, as of this writing (see
`docs/helps/roadmap.md`'s "MCP Server Ledger" for the full research):

- **OAuth-bridged** (Slack, Outlook, Teams, Gmail, Notion, GitHub,
  Linear, HubSpot, Jira, Confluence, Asana, Intercom, Pipedrive,
  Salesforce, Google Drive, SharePoint): the vendor's MCP server accepts
  an OAuth access token; bridged from the employee's OAuth connector
  account.
- **Static-secret-bridged** (Stripe, Trello, Airtable): the vendor's MCP
  server takes a plain API key as a Bearer token instead of OAuth — the
  employee pastes their own key once (Workspace → Connections), and
  that's what gets bridged in. No OAuth app registration needed for
  these three.
- **No MCP tool at all** (Zendesk, Telegram, Discord, SendGrid, Mailgun,
  Postmark): either the vendor has no official MCP server, or the one
  they have is a single-secret local process with no way to personalize
  per employee. The pre-built dataflow automation nodes remain the
  integration path for these — see Automation.

Outlook, Teams, and Gmail are the one exception to "vendor's own server":
seshat-server hosts those three itself (built before Microsoft/Google had
a usable offering), but they still go through the exact same per-employee
OAuth bridging as a real vendor-hosted one.
