## Self-service registration by email domain (MVP shipped 2026-07-15, email verification deferred)

Driven by a real onboarding concern: manually creating every new hire's account (or sharing a single join code/password across a whole company) doesn't scale, and a shared code is also a weaker security boundary than proving ownership of a company email address. `seshat-server` had no self-service account-creation path at all before this — `Bootstrap` is strictly single-shot (first platform admin only), `CreateUser` is admin-only, and `AcceptInvitation` requires an already-authenticated principal (it attaches an *existing* account to an org, it can't create a new one).

**Shipped now — the simple case, no email sending involved:**
- `Organization.domain` (nullable, unique) — an org sets its own email domain (e.g. `acmecorp.com`) via the normal organization settings form.
- `POST /api/v1/auth/register` (public, rate-limited separately from login) creates a `User` and, if the email's domain matches an organization's `domain`, immediately auto-joins them as a `Membership` with `status: "pending"` — full access already (identical to `"active"`), just flagged for admin attention. No domain match just creates the account with no memberships; the existing self-serve `CreateOrganization` covers "I'm the first person from a brand-new company."
- `status: "blocked"` is excluded from every authorization check (`canAccessOrganization`, `effectivePermissionsForPrincipal`, `membershipsByUser`) as if the membership never existed — verified live that an existing session gets a 403 the moment its membership is blocked, and a fresh login shows zero memberships for that org.
- `POST /api/v1/memberships/{id}/confirm` (admin, `members.manage`/`organization.manage`) finalizes a pending membership early. A periodic sweep (`iam.MembershipExpiry`, same Start/Stop/loop shape as `workspacechat.Cleanup`) auto-blocks any pending membership past `SESHAT_SERVER_MEMBERSHIP_CONFIRMATION_WINDOW` (default ~2 months) left unconfirmed.
- Console: `/register` page (public, mirrors `/login`), an "Email domain" field on the organization form, and a blue "New" tag + a one-click "Confirm" action on pending rows in Team & Access.
- Verified live end-to-end against a throwaway server (not the shared dev stack): register with a domain-matched email → pending membership with immediate access → admin confirm → separately, artificially aged a second pending membership and confirmed the sweep blocks it and that both an existing session and a fresh login lose access to that org.

**Deferred — a real design exists but isn't built:**
- No email actually gets sent anywhere yet (no SMTP/mailer package exists in `seshat-server` — checked, zero email dependency in `go.mod`). Planned: a small `internal/server/email` package (`Sender` interface, a `net/smtp`-based implementation — no new go.mod dependency needed — plus a `NoopSender` fallback when `SESHAT_SERVER_SMTP_HOST` is unset, same degrade-gracefully pattern as Docling being optional).
- Email-verify-before-anything: `User.PendingEmailVerification bool` (default `false` so existing accounts are grandfathered in as verified; deliberately this polarity, not `EmailVerified`, so new registrations can explicitly set it `true` without colliding with GORM's zero-value/`default:` tag omission behavior — a real gotcha hit and worked around elsewhere this same session). A hash-only verification token (same pattern as `Invitation.Token`/`sdb.HashOpaqueToken`), a new `POST /auth/verify-email`, and a console `VerifyEmailPage.tsx`. The domain-match-to-pending-membership step would move from register-time to verify-time, so an unconfirmed signup never pollutes Team & Access with a phantom pending row.
- An email notification to the organization's admins (v1 scope: whoever holds the `"owner"` role — deliberately not a full RBAC resolution of every custom role granting `organization.manage`) the moment a pending membership is created, so the 2-month window isn't the only signal an admin ever gets.
- A new `SESHAT_SERVER_CONSOLE_URL` env var (doesn't exist today) to build the clickable link inside the verification email.
- A resend-verification-email endpoint (not designed in detail, just noted as the natural next gap once the above exists).

## Direction: seshat-server becomes the multi-tenant backbone

Decided 2026-07-09: the platform is moving toward `seshat-server` as the multi-tenant cloud backend for everything, including file upload and knowledge/RAG — not just IAM and scheduled automation as today. `seshat-backend` (the existing local backend behind the desktop app) keeps working exactly as-is for the **local, single-user** case inside the desktop app; it is not being torn out — it gained a second, optional **connected mode** instead. This mode is *not* config-driven: `seshat-backend` decides at boot, on its own, whether a `seshat-server` deployment is reachable at a URL compiled into the binary (`defaultServerURL` in `seshat-backend/internal/config/bootstrap.go`), and falls back to standalone otherwise — deliberately not an environment variable, since `seshat-server` access is the paid managed-service tier and a configurable target would let anyone point a build at their own free self-hosted instance. See the root `README.md`'s architecture diagram and `docs/desktop-packaging.md`.

**Status as of 2026-07-14: 10 of 11 planned domains migrated and verified live** — Automation, Identity, Provider Settings, User Preferences, Skills registry, Web search config, MCP config, Memories (flat + long-term graph), Agents registry, Quotas (counters only). Each domain's exact scope, design forks, and end-to-end verification were meant to be tracked in detail in `helps/seshat-architecture-target.md` (§7) — **that file does not exist in the repository** (confirmed 2026-08-10, see `docs/helps/audit-2026-08-10.md`); treat this ROADMAP.md entry as the current source until it's recreated or the reference is removed. Only **Interactive sessions cloud** remains explicitly deferred: audited but found to need its own dedicated scoping pass (tenant model missing from `SessionStore`, billing/metering model undecided, session file-sandbox storage undecided) before implementation — not scheduled, no plan written yet.

## Knowledge base / RAG domain — first pre-built workflow (in progress, started 2026-07-09)

Picked as the first concrete pre-built workflow (see "Pre-built agentic workflows" below — this is workflow #2, the AI knowledge team / internal Q&A demo) precisely because the hard part already exists in the runtime, not because it's the easiest wedge on paper:

- `seshat/internal/rag` already has a complete `rag.Service` (`Ingest` + hybrid vector/BM25/reranker `Search`, namespaced by `corpus_id`), and the `rag_search`/`rag_ingest` tools are **already registered in every SDK client's tool registry** (`internal/tools/builtin/builtin.go`), gated by `IsEnabled() = RAGService != nil`. Nothing to build in the runtime itself.
- `automation.RunnerConfig` already has a proven precedent for wiring a tenant-scoped tool into cloud job execution: `WebSearchKeys map[string]string`, plumbed straight through to `sdk.ClientConfig` — adding an equivalent `RAGService` field is mechanical, not a new design.
- The embedder supports a plain OpenAI-compatible HTTP API (not just local Ollama) and the vector store has a `pgvector` backend — both fit directly into infrastructure `seshat-server` already runs (its own Postgres), no new infra component required.
- The real, only substantial piece of work is a **Corpus/knowledge domain in `seshat-server` itself**, which doesn't exist there at all today. `seshat-backend/internal/knowledge` (`Corpus`, `CorpusFile`, `KnowledgeIngestionJob`, single-instance polling ingestion worker, docling for PDF/DOCX/etc., search) is the direct blueprint — being adapted here as an **organization-scoped** equivalent (seshat-backend's version is per-user, single-tenant) rather than designed from scratch.

Build order:
1. **Done (2026-07-09).** Org-scoped `Corpus`/`CorpusFile`/`KnowledgeIngestionJob` domain in `seshat-server` (new `internal/server/knowledge` package): CRUD, multipart file upload via the runtime's `storage.ArtifactStore` (local disk or S3, config-driven — `SESHAT_SERVER_STORAGE_*`/`SESHAT_SERVER_S3_*` env vars, own namespace so it doesn't collide with a co-located seshat-backend/seshat-ui's storage config), async ingestion worker mirroring `automation.Scheduler`'s single-instance polling pattern (with idle backoff, closer to `seshat-backend`'s own knowledge runner). Two new permissions (`knowledge.read`/`knowledge.manage`) added to the catalog and to the owner/admin default roles — and, spotted while touching that list, `provider_settings.read`/`.manage` were missing from owner/admin too (a pre-existing gap from the earlier session), fixed in the same pass. `Ingest`/`Search` degrade gracefully with a clear "not configured" error until step 2 lands — verified end-to-end in tests using an in-memory vector store + a deterministic fake embedder (upload → auto-enqueue → process → ingested with chunks → search finds it). Routes under `/api/v1/knowledge/corpora/...`, documented in `openapi.yaml`. Binary-format ingestion (PDF/DOCX/audio via docling, which `seshat-backend` already wires up) is **not** ported yet — only plain-text/markdown/JSON/mostly-printable content extracts today; add docling once the demo needs it.
2. **Done (2026-07-09).** Platform-wide (+ org override) embedder configuration — `EmbedderSetting`/`PlatformEmbedderSetting`, same hybrid BYOK/platform-default shape as `PlatformProviderSetting`, but a **singleton** per organization (and one platform-wide), not a list — a corpus's vectors are all produced by whichever embedder was active at ingest time, so more than one active embedder per org risks silently mixing incompatible vector dimensions in the same namespace. Required a real refactor: `knowledge.Service` no longer holds one fixed `*rag.Service` — the embedder is resolved per call (org's own, else platform default) and a `rag.Service` is built ad hoc from the shared vector store (cheap, just a struct literal). The vector store itself is now real too: HNSW backend by default (embedded, no CGO, no external service, no bridging seshat-server's GORM connection into the runtime's own low-level DB handle — that bridging is what pgvector would need, deferred; HNSW just needs a directory, config via `SESHAT_SERVER_VECTOR_BACKEND`/`SESHAT_SERVER_VECTOR_HNSW_DIR`). Verified against a real running server: bootstrapped, set the platform embedder to point at a small local Python HTTP server mimicking the OpenAI embeddings API, uploaded a file over real HTTP, watched the ingestion worker pick it up and complete, then searched and got the file back — the full pipeline works for real, not just in unit tests. New endpoints `/api/v1/embedder-settings` (org) and `/api/v1/platform/embedder-settings`, both singleton GET/PUT(upsert)/DELETE, documented in `openapi.yaml`.
3. **Done (2026-07-09).** Wired `RAGService` through to cloud job execution. Required a small change in the `seshat` runtime itself (a separate git repo, vendored as a submodule at `seshat-ai/seshat`): added a `RAGService *rag.Service` field to `automation.RunnerConfig` (`internal/automation/runner.go`), mirroring the existing `WebSearchKeys` precedent exactly, plumbed straight to `sdk.ClientConfig.RAGService`. Committed locally in the submodule (commit `c98a7b0`, not pushed to the `nexus-engine` remote — the user's call, revisit before assuming it's shared/released) and the submodule pointer bumped in this repo. On the `seshat-server` side: `automation.Service` gained a `RAGResolver` interface (satisfied by `*knowledge.Service`, injected via `SetRAGResolver` in `app.go` after both services exist) so the `automation` package doesn't import `knowledge` directly — same "compose through an interface, don't couple bounded contexts" reasoning already used for `iam`. `executeCloudRun` now resolves a per-organization `RAGService` best-effort (a job with no embedder configured just runs without `rag_search` available, same as today — not a failure). The "cloud jobs are text-only" framing from earlier in this project is now more precisely "no local-machine access" — `rag_search`/`rag_ingest` are real tools a cloud job's prompt can ask the model to use, whenever an embedder is configured for that job's organization.

See item 8 below for full detail. **Not done**: a corpus picker on job creation specifically — the Jobs page itself is still a placeholder in the console (a pre-existing gap unrelated to RAG), so there's nowhere to add that picker yet; a job referencing a corpus today means writing `corpus_id='...'` into the job's free-text prompt by hand (that's genuinely all `CreateJobParams` needs — there's no dedicated corpus field on Job at all, so a "picker" would just be a UI convenience that fills in that ID for you).

Using Mistral (free tier, key from `seshat/private/.env.dev`) for both the embedder (`mistral-embed`, OpenAI-compatible endpoint) and the job's LLM (`mistral-small-latest`): configured both platform-wide, created a corpus, uploaded a short supplier-policy document, confirmed real ingestion (Mistral embeddings, 2 chunks), created a cloud-targeted `ScheduledJob` whose prompt asked a two-part question answerable only from the document, triggered it, and the run completed with the model correctly having called `rag_search` and answered both parts precisely (10% restocking fee on an 800 EUR non-defective return; escalation contact `vendor-relations@seshat.example` for disputes above 5,000 EUR) — both facts only existed in the uploaded document, so this rules out the model just guessing. The full three-step pipeline (steps 1–3 above) is now proven correct against a real model doing real tool-calling, not just unit tests and static code-tracing. This *is* the "AI knowledge team" flagship demo, run for real — turning it into a one-click reusable workflow (vs. hand-built via curl) is what step 4 (console) is for.

9. **Knowledge connectors, phase 1: S3, fully server-side (2026-08-19).** Closes a real gap surfaced while reviewing where `seshat-ai`'s existing S3/Google Drive/SharePoint "Knowledge connector" implementations lived: entirely in `seshat-backend`, tied to a paired device — meaning none of them could feed an org's knowledge base with no desktop app running anywhere, contradicting this section's own "seshat-server becomes the multi-tenant backbone" direction. `seshat-backend/internal/connector` and `internal/knowledges3` are ported (not imported — separate deployables, see `docs/architecture.md`'s runtime-boundary rule) into `seshat-server/internal/server/{connector,knowledges3,knowledgeconnectors}`, org-scoped instead of user-scoped: `ConnectorAccount`/`ConnectorSyncJob` (new tables), secrets under the organization's own DEK (`sdb.EncryptSecret`, not seshat-backend's flat AES-GCM), a `ConnectorSyncRunner` (same poll/backoff shape as `knowledge.Runner`) that reaps due accounts into jobs and processes them. Each synced item is handed to a new `knowledge.Service.IngestFromConnector`, which upserts a `CorpusFile` (new `ConnectorAccountID`/`ExternalResourceID` columns, for idempotent re-sync) and reuses `enqueueIngestionJob` unchanged — the exact same chunk/embed/vector-upsert pipeline a manual upload goes through, no parallel ingestion path. New endpoints under `/api/v1/knowledge/connectors/...`, console pages (Connectors list + S3 connect form + sync history), `docs/architecture.md`'s "Example: Knowledge connectors" documents the deliberate split from Inbox's still-device-tied design. Google Drive/SharePoint (OAuth-based) are the planned phase 2, reusing this same scaffolding plus `iam.Provider`'s org-scoped OAuth-app-credential pattern for the authorize/callback step. Verified via unit tests (`knowledges3`'s pure config/filter tests, ported from seshat-backend's) and an integration test exercising the full account→sync→upsert→ingest→re-sync-in-place→delete-preserves-files flow against a fake connector (no real S3 network needed to prove the wiring); `go build`/`go vet`/full `go test ./...` and the console's `tsc`/`oxlint`/`vite build` all clean.

10. **Cloud jobs' SDK client now gets a real ArtifactStore (2026-08-19, same day).** Raised alongside item 9 above: `S3` isn't only a Knowledge concern — `sdk.ClientConfig.ArtifactStore` (the runtime's own file-I/O backend for the bash/file tools) had no wiring at all in `automation`'s cloud-targeted job execution, so a cloud job's agent had its file writes falling back to `ClientConfig`'s own per-process local-disk default, discarded the moment that execution's short-lived client is closed (`Runner.Execute` builds and tears down a fresh client every call). Fixed the same way `RAGService`/`DoclingURL` were threaded through previously: added an `ArtifactStore sdk.ArtifactStore` field to `automation.RunnerConfig` in the `seshat` SDK repo (`internal/automation/runner.go`, propagated in `buildClientConfig`), then `automation.Service` in `seshat-server` gained `SetArtifactStore` (a plain setter, shared infrastructure not a per-tenant secret — same reasoning as `SetDoclingURL`, not `SetRAGResolver`), wired in `app.go` with the exact same `ArtifactStore` instance `knowledge.Service` already uses (same bucket/local-path, namespaced by key prefix — no separate config surface). **Important boundary note**: this SDK-side change lives only in the local `seshat` working copy as of this entry — `seshat-server/go.mod` has a **temporary `replace github.com/KPO-Tech/seshat => ../../seshat`** directive (see its comment) so the build/tests could run against it; it is not committed to the `seshat` repo's remote and no new tagged version exists yet. Someone needs to decide when to commit+push that SDK change and bump `seshat-server`'s pin to the real tagged release, then remove the `replace` — same "not pushed, the user's call" posture as the RAGService/DoclingURL SDK changes before it. Verified: `go build`/`go vet`/full `go test ./...` clean in both repos, plus a new `TestSetArtifactStoreWiresItIn` unit test.

11. **Knowledge connectors collapsed into one package (2026-08-20).** Item 9's 3-package split (`connector` interface + `knowledges3` implementation + `knowledgeconnectors` orchestration) mirrored `seshat-backend`'s own layout, but a closer look found neither `connector` nor `knowledges3` had ever gained a second importer — both existed solely for `knowledgeconnectors`, so the extra package boundaries bought isolation nothing else used, at the cost of navigating three directories to understand one feature. ## Interactive sessions in seshat-server (proposed 2026-07-09, not started)

User's proposal, explicitly deferred until the RAG console UI (above) is finished — noted here in full so the shape is captured before it's lost, not because it's next in line.

**The gap this closes**: everything built so far (`automation`'s `ScheduledJob`/`JobRun`) is one-shot — a prompt goes in, one final answer comes out (`jobWorkflow.Run` calls `session.SubmitMessage` exactly once, then the run is done). There is no multi-turn, persistent, streamed conversation in `seshat-server` today. The runtime's own `sdk.Session` already supports that (multi-turn, tool use, streaming deltas via `ResponseChunkFn`) and `seshat-backend` already implements a full interactive chat system locally on top of it — but nothing in `seshat-server` exposes an equivalent for multi-tenant/cloud use.

**What the user wants this to unlock**:
1. The same workflows built as one-shot jobs (the RAG/knowledge-team demo, and future ones) usable as **real conversations**, not just scheduled fire-and-forget runs.
2. `seshat-ui` (the desktop app) able to point at a `seshat-server` instance instead of (or alongside) the local `seshat-backend` — an "enterprise/multi-tenant mode" for the same desktop app, not a separate build.
3. Longer-term: richer session output — audio and eventually video generation, "like NotebookLM" — which is the same multi-modal ambition already tracked under "Multi-modal provider config" below, just applied to a live session instead of a one-shot job.
4. Even longer-term: a **separate, standalone web app** that talks only to `seshat-server` (no `seshat-backend` involved at all) — pitched specifically as a client-facing demo/sales tool for the business, not an admin surface like `seshat-console`.

**Why this is a bigger epic than everything built for RAG combined, and needs its own scoping pass, not an ad-hoc build**:
- **Different execution model, not an extension of `cloud_execution.go`.** Jobs build a fresh SDK client per execution and throw it away. A session needs to stay "live" across turns (or be cheaply reconstructible with full history), needs real-time delivery to a client (SSE or WebSocket — `ResponseChunkFn` already exists in the SDK, but `seshat-server` has never had to stream anything to an HTTP client before), and needs message-history persistence (a new DB domain: sessions + messages, org-scoped).
- **Auth/routing implications for `seshat-ui`.** Today `seshat-ui` assumes "local backend, always the one local user." Pointing it at `seshat-server` means a real login/org-selection flow inside the desktop app, not just a different base URL.
- **This is where the still-undecided subscription/billing system (below) stops being optional.** A scheduled job runs occasionally and finishes; an interactive session can run indefinitely and burn tokens continuously — usage-based billing has real teeth here in a way it didn't for periodic jobs.
- **Console/admin implications**: `seshat-console` would presumably need session visibility (list active/past sessions per org, maybe cost/usage) — another surface, not built.

**Recommended shape when this is picked up** (a starting hypothesis, not a decision): a new `internal/server/sessions` domain in `seshat-server`, mirroring `seshat-backend`'s own session/chat implementation the same way `knowledge` mirrored `seshat-backend`'s knowledge domain — read that code first rather than designing from scratch. Scope the *first* version to text-only, reusing everything already proven this session (hybrid provider settings, `rag_search`/`read_document_url` tool wiring), before adding audio/video.

**Also raised in the same discussion**: bundling and deploying a **curated set of useful MCP servers together**, once, as part of the stack — instead of one-off tool integrations (like the Agent-Reach discussion above). The runtime already has a first-class MCP client (`internal/tools/system/mcp`); the idea is a docker-compose-deployed set of MCP servers (candidates: something Exa-search-like, GitHub, others TBD) that any session or job — local or cloud — connects to for a consistent, "batteries-included" tool set, rather than writing bespoke Go tools per capability. Not scoped in detail — surfaced here so it's not lost, worth designing alongside the sessions epic since sessions are exactly where richer tool access matters most (a one-shot job's prompt is narrow and known in advance; an open-ended conversation benefits far more from a broad tool set).

## Multi-modal provider config (image, audio, web search)

Today only LLM has a config domain (`ProviderSetting` per org + `PlatformProviderSetting` platform-wide fallback), matching `GOAL.md`'s Level 4 ambition (image generation, audio, eventually 3D). Extending the same hybrid model to the other modalities means, per modality:

- A new settings domain (e.g. `ImageProviderSetting`, `AudioProviderSetting`), org-scoped + platform-wide default, same encryption-at-rest / redaction pattern already proven for LLM.
- Execution wiring: today `automation.Runner` (absorbed from `seshat/pkg/automation`) only ever calls `session.SubmitMessage` — no tool is registered, so a cloud job cannot call an image/audio/web-search backend even if credentials existed. Wiring image/audio generation into a job means either registering real tools on the executor's SDK client, or a dedicated non-job code path (e.g. a direct "generate image" API endpoint outside the job/run model entirely). **This needs a design decision before implementation** — it changes the "cloud jobs are text-only, structurally" boundary that's currently deliberate, not accidental (see automation package memory notes).
- Web search specifically also needs a decision on provider choice/config shape — `seshat-backend` already has local env-var-based web search config (Tavily/Exa/Jina/SearXNG); whether `seshat-server` gets its own independent config or something shared/proxied through `seshat-backend` is undecided.
- Console: one page per modality, org-level + platform-level, following the same drawer/table pattern as the LLM provider settings pages already built.

**Open questions to resolve before starting:** which providers to support first per modality (e.g. one image backend to prove the pattern rather than all of Stable Diffusion/FLUX/DALL-E at once); whether cloud jobs gain tool access at all or this is a separate non-job API surface; whether these are billed/metered from day one or bundled in with the still-undecided subscription system below.

## Subscription / billing system

Explicitly deferred multiple times so far (audit: "billing/plan tiers by member count deferred as a separate unbuilt commerce feature"; Casdoor comparison: all commerce confirmed out-of-scope). It resurfaces now because the hybrid BYOK/platform-default provider model implies a real "pay Seshat, don't bring your own key" business model — this is the connective tissue between "superadmin configures defaults" and "customers pay to use them."

This is a large, separate subsystem that deserves its own scoping pass, not a bullet point implemented incidentally. Known shape, **not yet decided in detail**:

- Plan tiers (likely per-organization, possibly by member count and/or usage volume — precedent already noted in the self-serve org creation decision).
- Usage metering: tokens/requests against the platform-default provider credentials, per organization, per period.
- Quota enforcement: what happens when an org exceeds its plan (hard block vs. degrade vs. bill overage) — nothing built here yet, not even a counter.
- Payment provider integration (Stripe is the default assumption, unconfirmed) — subscription lifecycle (trialing/active/past_due/canceled), webhooks, invoicing.
- Whether BYOK organizations (bringing their own provider key) are exempt from usage billing entirely, or still pay a seat/platform fee — directly affects how "hybrid" the hybrid model really is commercially, not just technically.

**Recommended first step when this is picked up:** a dedicated design/planning pass (not a coding session) to answer the questions above before any schema or endpoint is written — this is exactly the kind of decision that's expensive to unwind once org data and billing history exist.

## Pre-built agentic workflows

Raised as a want (`create organizations/members... and pre-created agentic workflows`). Cross-checked against `website/src/pages/services/` (2026-07-09) — the marketing site already commits to three concrete flagship workflows, one per service wedge, each with a scripted terminal demo in `ServicesHero.tsx`. These are the natural first candidates for a real template catalog rather than starting from a blank page:

1. **Document processing → KYC/KYB file validation.** Demo: `ServicesHero.tsx`'s "Validate KYC file #2847" — OCR + extraction, identity-document validity check, address-proof freshness check, registry-extract age threshold, drafts a follow-up email when something's borderline, human approval before finalizing. Adjacent workflows in the same wedge per `ServicesGrid.tsx`: claims processing, contract review/extraction, compliance checks, HR file processing.
2. **AI knowledge team → internal policy/procedure Q&A.** Demo: "Answer new supplier policy questions" — hybrid retrieval over internal PDFs/procedures, source-cited answers, workspace access boundaries respected. Adjacent: support-ticket assistance, onboarding assistant.
3. **Back-office/finance → cash reconciliation.** Demo: "Close Q2 cash reconciliation" — matches bank exports against ERP records via accounting rules, generates a VAT summary, flags anomalies for operator confirmation, drafts the report. Adjacent: inbox/email triage and routing, approval workflows, escalation and response prep.

**Mismatch found and resolved (direction only — not built yet):** `Process.tsx` (the site's own "Delivery model" section) describes today's actual engagement model as bespoke and consulting-led — "Scope the workflow → Design the pilot team → Implement and review → Deploy or expand" — not self-serve template-picking. So "pre-built workflows" could have meant either an internal accelerator for the delivery team, or a self-serve catalog for customers. Asked the user directly (2026-07-09); decision: **build both, from one system, not two** — explicitly not now, but this is the shape to build when it's picked up:

- **One `WorkflowTemplate` domain**, curated by the platform admin exactly like `PlatformProviderSetting` today (superadmin authors/edits templates; no separate org-authored templates for v1).
- **One catalog UI in `seshat-console`**, gated per-organization by a `required_plan`/`visibility` field on the template, not by a separate internal-only surface. The delivery team instantiates from the same catalog to scope a new client pilot quickly (logged in as platform admin, or as a temporary member of the client's org); the client keeps using the identical catalog afterward, self-serve, with only the templates their plan entitles them to shown as instantiable.
- **Rationale for one system over two:** an internal-only library and a customer-facing catalog map to the same underlying idea (a good job configuration, reusable) — maintaining them separately guarantees drift. Gating by plan is also the natural on-ramp for turning a free-tier KYC/reconciliation/Q&A demo into a paid feature, which ties directly into the still-undecided subscription system above rather than being invented separately.
- Still open when this is picked up: whether instantiating a template just pre-fills the create-job form or also tracks drift from the template it came from; whether templates get their own `seshat-server` domain from day one or start as a static catalog shipped with `seshat-console` for a simpler first cut.

## Prospecting/CRM domain — local + cloud, shared core extracted (2026-08-10)

**Correction (2026-08-10, same day):** the original 2026-08-10 audit (`docs/helps/audit-2026-08-10.md`) claimed `seshat-backend/internal/prospecting` was "entirely unwired — zero HTTP routes, zero tool registration, zero reference in app.go." That was wrong: the audit agent grepped `internal/api internal/query internal/agents internal/prompt` but never checked `internal/config/bootstrap.go`, which is where the actual wiring lives. Verified directly: `bootstrap.go` constructs `prospecting.Service` whenever `prospecting.IsConfigured()` (`GOOGLE_PLACES_API_KEY` set), and registers `prospectingtool.NewSweepAreaTool`/`NewListBusinessesTool` globally — the exact same pattern as `knowledge_search` (env-gated, any agent can call them via chat, no dedicated seshat-ui page, same as Knowledge Agent's tool). This has been true since before this session started (commit `cb0dffe`). Third audit finding this session that didn't survive real verification — see the addendum in `docs/helps/audit-2026-08-10.md` for the other two (`SESHAT_SERVER_URL`, `requireRole` on `/skills/repos`).

**Decision, revised from the original "move to seshat-server, don't wire locally" call**: prospecting follows the same local-first-plus-optional-cloud shape as every other dual-mode domain in this app (Inbox, Knowledge, MCP, agents, web search) — local usage (chat-triggered sweeps, works while the app is running, no organization needed) stays and keeps working exactly as it does today; a future org-scoped `seshat-server` domain adds 24/7 recurring sweeps, the same relationship Scheduling/cloud automation has to the Inbox Agent's local-only assist mode. Cloud-only would have been the one domain in this codebase breaking that pattern for no good reason.

**Done (2026-08-10):** the tenant-agnostic ~900 lines (geocoding, grid tiling, the Google Places client, French company-registry enrichment, reachability scoring, name-similarity matching, HTTP response caching) were extracted out of `seshat-backend/internal/prospecting` into a new sibling Go module, `prospecting-core/` (module `github.com/EngineerProjects/seshat-ai/prospecting-core`, added to `go.work`). This is the first shared-package-across-backends pattern in this codebase — deliberately not generalized to knowledge/memories/mcp/quotas/preferences, which already delegate their real logic to the `seshat` runtime (`pkg/rag`, `pkg/memory/longterm`, `pkg/mcp`) or are too thin to be worth it; prospecting was the exception because its real logic was written directly in `seshat-backend` rather than the runtime, and it's substantial enough (~900 of ~1850 lines) to be worth not duplicating. Two small interfaces (`Cache`, `UsageTracker`) replace the direct `internal/db` dependency the moved code used to have; `seshat-backend/internal/prospecting` now implements a thin adapter (`adapters.go`) and keeps only what's genuinely tenant-shaped: `Sweep` (has `UserID`), persistence, and ownership checks. Verified behavior-preserving: all 8 `internal/prospecting` tests plus 7 `internal/prospectingtool` tests still pass unchanged.

**Not scheduled, no plan written in detail yet** for the cloud side. Shape when picked up — now smaller than originally scoped, since the algorithm core no longer needs porting, only tenancy/persistence/routes:

1. New `seshat-server/internal/server/prospecting` domain, organization-scoped, importing `prospecting-core` directly (no algorithm porting needed) plus its own `Sweep`-equivalent with `OrganizationID`, its own DB models, and adapters satisfying `prospectingcore.Cache`/`UsageTracker` against its own store.
2. New DB models in `seshat-server/internal/server/db` mirroring `prospecting_cache_entries`/`prospecting_daily_usage`/`prospecting_sweeps`/`prospecting_businesses`, org-scoped instead of user-scoped (same "mirror seshat-backend's own struct field-for-field" pattern already used for `Corpus`/`UserMemory`/`MemoryEntity`).
3. New permissions (e.g. `prospecting.read`/`prospecting.manage`), added to the catalog and owner/admin default roles — same pattern as `knowledge.read`/`knowledge.manage` when that domain was added.
4. HTTP routes under `/api/v1/prospecting/...` for recurring/24/7 sweeps via `automation`, documented in `openapi.yaml` — the local chat-tool path stays as the always-available fallback, same relationship Inbox has to Scheduling.
5. A `prospectingtool`-equivalent registered as real agent tools for cloud-targeted jobs, mirroring the `RAGResolver` precedent in "Wired `RAGService` through to cloud job execution" above.
6. `seshat-console` UI once the domain is real and tested — not before, same order the RAG/knowledge work followed.

`seshat-backend/internal/prospecting` and `internal/prospectingtool` are **not** going away — they're the permanent local implementation, not a temporary blueprint to delete once the cloud port lands.
