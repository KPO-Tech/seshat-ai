When people talk about "modes" they usually mean one of three different things. Seshat keeps them separate.

| Question | Setting | Values |
|---|---|---|
| **How do I reach the runtime?** | Entry surface | Terminal (CLI), Go SDK, gRPC server |
| **How does it behave?** | Execution mode | `execute`, `plan` (`pair_programming` exists but does nothing yet) |
| **Who approves what it does?** | Permission mode | `onRequest`, `acceptEdits`, `auto`, `never`, `granular`, `bypass` |

You can combine them freely: for example, `plan` mode with `onRequest` approvals through the SDK.

## Entry surfaces

All surfaces drive the same runtime, so the same sessions, tools and providers are behind each of them.

- **Terminal**: `seshat chat` and `seshat run`, for your own work.
- **Go SDK**: `sdk.NewClient`, to embed an agent in an application.
- **gRPC server**: `cmd/grpc`, to run the agent as a service for other programs. The gRPC surface is experimental and partial: one service, `SeshatService`, with `Query`, `QueryStream`, skills, MCP, models and health methods. See the [gRPC API](/en/docs/sdk/grpc-api).

## Execution modes

| Mode | What it does today |
|---|---|
| `execute` | The default. Tools run normally |
| `plan` | The agent explores, asks you questions and writes a plan, then asks you to approve it before it starts changing things |
| `pair_programming` | Defined, but nothing in the runtime changes its behaviour yet: it only shows as a label in the terminal interface |

### Plan mode

<Diagram {...planMode} />

The agent enters plan mode by calling the `enter_plan_mode` tool, or a Go host can do it with `session.ForcePlanMode()`. It then receives instructions: explore with read-only tools, ask about unclear requirements, design the steps, and call `exit_plan_mode` with the full plan. You are asked to approve the plan. On approval the plan is saved to a file, the earlier permission mode comes back, and the agent starts implementing, usually with the task tools.

<Callout type="warning" title="What plan mode refuses">
In plan mode, writes and edits are **refused**: `write_file` and `edit_file` are denied outright, so the agent cannot change a file while it plans. The plan itself does not go through those tools: `exit_plan_mode` saves it. The other tools, the shell included, are still governed by the permission mode, so plan mode is not a full read-only sandbox. If you need a strictly read-only agent, restrict its tools: the `explore` sub-agent only has read tools.
</Callout>

## Permission modes

These decide who approves the agent's actions, not what it does. The full table is in [Using the CLI](/en/docs/guides/cli#permission-modes).

<Callout type="tip" title="Where to start">
Keep `execute` with `onRequest`. Move to `plan` when you want to read the plan first, and to `never` for background jobs that must not wait for you.
</Callout>
